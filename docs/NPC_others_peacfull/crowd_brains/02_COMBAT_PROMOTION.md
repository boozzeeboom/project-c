# 02 — Промоут на стычку: «пнул → бьют (но не все)»

> Механика: игрок бьёт любого видимого. Сервер включает мозг самому ударенному + 2–7 соседям. Остальная толпа остаётся клиентской.

## 2.1 Почему «мозг каждому» невозможен, а «пнуть каждого» — возможно

Развести два требования:

- **R-hit (пнуть):** нужен только адресат урона + HP + позиция для проверок. Это реализует `IDamageTarget` (`Scripts/Combat/Core/IDamageTarget.cs:13–47`) — чистый интерфейс: `GetPosition / GetCurrentHp / ApplyDamage / IsAlive / GetTargetId`. Ему не нужен `GameObject`, `NavMeshAgent` или `NetworkObject`. Серверная строчка ростера может его реализовать напрямую. `CombatServer` (`Scripts/Combat/Network/CombatServer.cs:178`) работает со словарём `targetId → IDamageTarget` — ему всё равно, тело это или запись.
- **R-fight (драться):** нужны тик, навигация/позиционирование, кулдауны, `ResolveAttack` в ответ, аниматор, репликация. Это дорого (см. `01 §1.4`). Поэтому R-fight выдаётся только по лизе из `BrainPool`.

Вывод: **все имеют R-hit всегда, R-fight — только герои.** Игрок не отличит: ударенный вскрикнул и схватился (клиентская реакция, 0 сервера), а через долю секунды 1–4 реально пошли бить (герои).

## 2.2 Сущности боя

- **CrowdHitProxy (сервер, данные).** Реализация `IDamageTarget` для `crowdId`. Поля: `crowdId, targetId (синтетический), anchorId, coarsePos, hp, maxHp, factionId, attitudeRef, state: Idle|HeroCombat|Down|Dead`. Никакого `Update`. Зарегистрирован в `CombatServer`-реестре наравне с `NpcTarget`/`PlayerTarget`.
- **targetId для толпы (синтетика).** `NpcTarget.GetTargetId()` сегодня возвращает `NetworkObjectId` (`Combat/Implementations/NpcTarget.cs:97`). Для толпы без `NetworkObject` нужен непересекающийся диапазон — тот же приём, что уже принят для NPC-кораблей: sentinel старший бит (`NpcInstanceId = NetworkObjectId | 0x8000_0000_0000_0000`, см. `npc_ship/03_V2_ARCHITECTURE.md §4.1`). Предлагается: `crowdTargetId = zoneHash48 | 0xC000...` (префикс «толпа»), проверка `IsCrowdTarget(id)` одним сравнением. Коллизии с `clientId` (малые числа) и `NetworkObjectId` исключены диапазоном.
- **CoarsePos (грубая позиция).** Серверу не нужна точная поза каждого из 150. Достаточно `anchorPos + slotOffset` (якорь известен из ростера, смещение детерминировано сидом или последним `HERO_DOWN`). Точности хватает для `MeleeRangePolicy/RangedRangePolicy` + LOS-рейкаста (`CombatServer.cs:206–242`) с допуском: для толпы дистанция проверяется с запасом +0.5–1.0м в пользу игрока (чтобы не было «я точно попал, а сервер сказал OutOfRange» из-за рассинхрона клиентской петли).
- **BrainPool (бой).** N слотов серверного combat-тика на зону. Стартовая гипотеза: **6 слотов на «Гигант», 8 на квартал города, + кап 3–4 атакующих на одного игрока** (остальные повышенные — «на подхвате»: орут, окружают, зовут стражу, но не бьют одновременно — иначе фокус-дамаг убьёт баланс).
- **FightLease.** `{slotId, crowdId, victimClientId (обидчик), expiresAt, renewOnDamageOrAlarm}`. TTL стартовый 20–30 с. Продлевается уроном по герою/от героя, `Alarm`-событием, смертью союзника рядом (`allyDeathRadius=20` уже есть в `NpcSocialBrain.cs:72`). Не продлелась → демotion.

## 2.3 Пошаговый сценарий «пинок в толпе»

```
0. Было: 40 видимых на палубе, 0 героев. Ростер: 150 записей Idle.
1. Клиент: игрок бьёт (кулак/оружие) → обычный RequestAttackRpc(crowdTargetId, sourceId).
   Клиент НЕ решает, попал ли; он просит сервер рассудить (как сейчас).
2. Сервер Validate (тот же код, что для NPC):
   - attacker/target зарегистрированы? cooldown? (CombatServer.cs:180–204)
   - дистанция (с допуском толпы) + LOS-рейкаст; при чужом IDamageTarget на пути —
     перенаправление урона в него (уже есть, CombatServer.cs:209–232);
     для толпы это даёт бесплатно «попал не в того, а в соседа».
3. Сервер ApplyDamage в CrowdHitProxy: hp -= finalDamage.
   Параллельно: GrudgeTable.RecordHit(обидчик) + attitude -2 (тот же вызов, что
   NpcBrain.cs:595–596 делает для полных NPC — вынести в общий хелпер ростера).
   Клиентам-наблюдателям: дельта HP + хит-флеш (тонкая, не тик).
4. Сервер решает повышение (см. §2.4): ударенный + соседи в alarmHearingRadius=15м.
   Кандидаты фильтруются: жив? не в лизе? personality храбрый (см. §2.5)? слоты есть?
5. Сервер Admit+Bind: первым — ударенному (приоритет), дальше — по храбрости/близости,
   пока не кончится пул. Каждому: HERO_UP наблюдателям
   {crowdId, targetId, seed внешности, anchorHint, reason: Combat, ttl}.
6. Клиенты переводят эти визуалы в combat-стойку (анимация + бейдж), остальные 35+
   играют flee/cower-разбегание локально (дешёвый клиентский steering по петлям,
   без сервера).
7. Герои тикают по-боевому (упрощённо, см. §2.6) и бьют в ответ через тот же
   ResolveAttack (attackerId героя — его crowdTargetId, зарегистрированный как
   IAttacker-эквивалент; кулдауны общие).
8. Тишина 20–30 с / цель сбежала за leash / герой умер → демotion (§2.7).
```

Задержка между пинком и ответом — 1–2 серверных тика (десятки мс) + сеть. Игрок воспримет как реакцию, а не как спавн.

## 2.4 Кого повышать: формула допуска

Не всех соседей, а по приоритету (порядок важен — пул маленький):

1. **Ударенный** — всегда первый кандидат (если жив и не в лизе).
2. **Охрана/стража** (`isGuard`, `NpcSocialBrain.cs:73`) в `alarmHearingRadius` — вторыми, вне зависимости от храбрости.
3. **Соседи по храбрости**: `personalityConfig` (уже есть `NpcSocialBrain.cs:30`) + `fleeHpThreshold`/`surrenderHpThreshold` + отношение к обидчику (`HasGrudge`, `hostilityThreshold` из `NpcBrain.cs:110`). Трус с `canFlee` — не кандидат в бойцы, он кандидат в беглецы (и это правильно).
4. **Лидер группы**: если ударенный в группе (`NpcGroupController`), повышается лидер, остальные — по бюджету.

Стоп-условия (не повышать): `Neutral` (манекены), `Down/Dead`, уже в диалоге с другим игроком (диалоговая лиза старше боевой? см. `06`), нет слота в пуле, обидчик вне `threatEvaluationRange`/уже сбежал.

Число «2–7 соседей» из вопроса — это и есть размер волны: **1 (ударенный) + до 2–3 бойцов + до 2–4 «шума» (орущие/зовущие, без combat-тика, только скрипт + вокал)**. «Шум» не ест BrainPool — ему достаточно одноразовой команды.

## 2.5 Кто вообще дерётся, а кто бежит (характеры, а не рандом)

У нас уже есть всё для неоднородной реакции (`NpcSocialBrain.cs:57–106`): `canFlee/fleeHpThreshold`, `canSurrender/surrenderHpThreshold`, `coverHpThreshold`, `personalityConfig`, `faction`, `isGuard`, `morale`-задел (`NpcMoraleData`), `grudge/vengeance`, `postCombat` (ранен/лечится/зовёт подмогу). Теория требует только распространить это на ростер (хранить те же 5–6 чисел на `crowdId`), а не тикать.

Матрица реакции на удар (первый удар, до повышения):

| Тип | Клиент мгновенно (0 сервера) | Сервер следом |
|---|---|---|
| Храбрый/страж/обиженный (`HasGrudge`) | стойка, крик (`NpcVocalCue`) | кандидат №1 в BrainPool |
| Обычный | отшагнуть, крик | кандидат при свободном слоте |
| Трус (`fleeHpThreshold` высокий) | `ForceFlee`-эквивалент локально | не повышать, записать обиду |
| Сдающийся (низкое HP/нет союзников) | руки вверх (`Surrendered`-поза) | не повышать, пометить `surrendered` (бить его — штраф отношения, см. репутацию) |
| Страж вне радиуса | — | `Alarm` волной: ближайший патруль получает лизу и идёт (как `postCombatGuardMin/Max`, `reinforcementSeekRadius=50`) |

## 2.6 Как дерутся герои (упрощённо, не полный NpcBrain)

Полный `NpcBrain` (Idle→Chase→Attack + `SocialBrain.Tick` + NavMesh-погоня) для героев толпы избыточен и вреден в тесноте. Герою толпы достаточно **Brawl-режима**:

- **Без погонь по NavMesh на палубе/в аллее.** `SetDestination` в толпе = заторы и фликер (наш же урок с «Гигантом»). Герой дерётся там, где стоит: `FaceTarget + Attack + separation-push` от соседей. Погоня — только шагом к цели в прямой видимости до `attackRange × 1.3`, дальше — сброс в `leash` (как `HandleChase/HandleAttack` в `NpcBrain.cs:1101–1153`, но без агента).
- **Тик реже.** Герои толпы тикают 5 Гц, а не 10; `SocialBrain.Tick` для них — только `threat/flee/surrender`-проверки, не полный patrol/grudge-скан.
- **Один думает за группу.** Повышенная группа получает общий `aggroTarget` (обидчик) и общий кулдаун-стаггер (не бьют одновременно — разнос 0.3–0.6 с), иначе 4× урон в один тик.
- **Ответный урон — через тот же `ResolveAttack`.** Герой как `IAttacker` с `defaultSourceId=0` (как `TryAttack` в `NpcBrain.cs:1155–1180`), плюс опционально `NpcSkillSet` только у «элиты» (стража). Толпе не нужны скиллы/AOE — это цена, которую платит баланс за массовость.

## 2.7 Демotion после драки (обязательно, иначе пул умрёт)

Условия демоута (любое первое):

- TTL лизы истёк и не продлён уроном/тревогой;
- цель мертва/сбежала (`leashRange × 1.5`, как `NpcBrain.cs:1038`) или герой умер;
- игрок ушёл из AOI (наблюдателей нет — думать не для кого).

Процедура:

1. Сервер снимает combat-тику, возвращает слот в пул, пишет в ростер итог: `hp, alive/dead, grudgeUntil, attitudeDelta, surrenderedFlag, anchorHome (вернуть на дом-якорь!)`.
2. Рассылает `HERO_DOWN {crowdId, outcome: Calm|Fled|Down|Dead|Surrendered}` наблюдателям.
3. Клиенты переводят визуал обратно в петлю/якорь (умерший — в лежание + затем лутинг по правилам `04`).
4. Убитые решаются по `respawnPolicy` ростера (аналог `ShipCrewManifest: Never|OnShipSpawn|AfterDelay`): толпа обычно `AfterDelay` с новым сидом внешности («пришёл другой докер»), именные — `Never` без квеста.

Важно: **дом-якорь свят.** Герой после драки не остаётся там, где упал/стоял, — он возвращается (телепорт-возврат при демоуте, если никто не видит, или доводка по петле). Иначе за день толпа сползёт в одну точку.

## 2.8 Корабельная специфика

- Драка на палубе — всегда Brawl-режим (нет `SetDestination`, нет прокси-агентов `NpcDeckNavProxy`). Герои — дети `ShipRoot`, координаты — локальные (см. `05`). Серверный range-check — в локальном кадре корабля (дешевле и точнее, чем мировые).
- Падение за борт/под винт: отдельное правило (урон окружения, не бой) — вне этого файла, пометить для `04`.
- `platformCarry`/`TrySetParent` (`NpcBrain.cs:322–344`) героям толпы не нужен: они уже дети корабля. Это одна из главных экономий схемы.
