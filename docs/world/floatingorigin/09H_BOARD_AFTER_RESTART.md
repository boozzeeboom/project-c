# T-FO09H — Посадка на корабль выхода после рестарта (регрессия FO)

Date: 2026-09-13. Жалоба (ф8_27): выход на корабле → перезаход: корабля
рядом нет, падение, город. Раньше: спавн на своём корабле; спрыг с корабля →
респавн на корабле.

## Диагноз по ф8_27 (точечно)

- Пилотный старт: `local=(80205.87, 5036.06, 81500.23)` — сырая позиция
  сейва (точка корабля на момент выхода), `inShip=False` все 311 записей.
- Автосдвиг штатен (frame=2, origin `[80128,4864,81408]`), дальше падение
  `(78.44,-5104.11,92.23)` → респавн на несдвинутый fallback
  `(-40293,-2331,-41405)` (билд лога без 09G/09G-fix — отдельная история).
- Корень: два пути восстановления разошлись. Legacy `RestorePlayer`
  умеет inShip (поиск по `ShipPersistentId` → `GetExitPosition`), но
  global-ветка `RestorePlayerPositionCoroutine` делает `yield break`
  ДО него (PERSIST03): pilot ставит игрока по сырым координатам, а корабль
  ресторится позже (~3.5с). Игрок падает рядом с пустым местом. До FO
  legacy-путь работал — регрессия FO-эпохи.
- Сейв проверен напрямую (`ShipPositions.json`): запись игрока/кораблей
  консистентна; текущий файл уже перезаписан падением (inShip=False) —
  для теста нужен выход НА корабле.

## Решение

1. `ShipPositionServer.TryLoadPlayerShip` — чтение inShip/shipId из сейва
   (сдвиг не нужен, только ID).
2. `NetworkPlayer`: global-ветка корутины при inShip-записи ждёт
   `RestoreCompleted` и телепортирует на exit живого корабля
   (`WaitForShipAndBoard`, только сервер, сброс fall-таймера + порог).
   Корабля нет — старое поведение (pilot-точка). Без inShip-записи —
   без изменений.

## Проверка

1. Compile: `refresh_unity` (force + compile) — PASS; `read_console` —
   0 errors, 0 CS; скобки 362/362, 53/53.
2. Play Mode (user): выход НА корабле → перезаход → `boarded restored
   ship '<id>'`, игрок на exit корабля, падения нет. Спрыг с корабля →
   автореспавн на корабль (цепочка 09C, была и осталась).
