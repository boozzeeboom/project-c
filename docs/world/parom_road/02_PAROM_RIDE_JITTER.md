# Паром — дёрганье райдера на кабинке (T-PAROM-04)

> Статус: причина найдена, паромный фикс внедрён (клиентское сглаживание).
> Общий carry (`NetworkPlayer.ApplyPlatformCarry`) НЕ трогали — чинили только сторону парома.
> v1: `00_PAROM_DESIGN.md`. v2-план: `01_PAROM_V2_PLAN.md`.

## 1. Симптом

Стоя на движущейся кабинке, персонаж немного дёргается. Зависит от скорости
кабинки и от изменения высоты (ложбины провисания тросов). Увеличение
`_platformProbeDistance / _platformProbeRadius` у игрока ситуацию не меняет.

## 2. Причина (паромная, не в carry)

Разбор общего carry — в ресёрче moving-platform (сеть/фазы Update/FixedUpdate).
Здесь — только то, что специфично парому. Причин три, все на стороне `ParomRoute`:

1. **Ступенька тик-рейта (главная).** Сервер пишет `_netS` каждый `Update`
   (`ParomRoute.cs: PublishNet`), а клиент ставит кабинку по сырому `_netS.Value`
   (`s = _netS.Value`). NetworkVariable приезжает с тик-рейтом сети, а не с кадром:
   при 9 м/с и ~30 тиках кабинка на клиенте едет рывками ~0.3 м на тик.
   Carry-дельта превращается в «0, 0, 0, БОЛЬШАЯ» — райдер дёргается ровно
   в такт сети. Вертикаль страдает сильнее: кабинка идёт по провисшей параболе
   (`SaggedPoint`), вертикальная компонента меняется нелинейно внутри шага.
2. **Трансформ вместо физики.** `ApplyTrolley` двигает кинематический Rigidbody
   прямой записью `_trolley.position / rotation`, а проб игрока —
   `Physics.SphereCast` по физическому состоянию (синхронизируется в FixedUpdate).
   Зонд видит кабинку с опозданием на фазу. У кораблей палуба едет физикой
   (`linearVelocity / MoveRotation`) — консистентно; у парома — нет.
3. **Разворот на 180° на конечных.** `_trolley.rotation = LookRotation(moveDir)`,
   при смене `dir` в `Arrive` yaw прыгает сразу. Carry-yaw честно переносит это
   как орбитальное смещение — разовый рывок стоящего пассажира.

Почему Probe-параметры не помогли: `_platformProbeDistance / _platformProbeRadius`
влияют только на **детект** (достанет ли SphereCast до пола), а не на гладкость
дельты. Это ожидаемо.

## 3. Фикс T-PAROM-04 (только `ParomRoute.cs`, серверная симуляция не менялась)

- **Сглаживание `s` на клиентах** (экспоненциальное, `tau = _clientSmoothTime`,
  дефолт 0.12 с). Сервер/хост едут по точному `_serverS` без запаздывания;
  удалённые клиенты догоняют сеть гладко. Абсолютное отставание на ~tau
  неважно — райдер едет **дельтой**, а не абсолютной позицией, а дельта
  становится гладкой. Первый кадр и скачки > `_clientSnapDistance` (дефолт 8 м:
  вход на маршрут, телепорт) — снап без сглаживания.
- **Доворот кабинки на клиентах** (`RotateTowards`, `_clientTurnSpeed`,
  дефолт 90°/с). Разворот на конечной происходит во время стоянки и виден как
  плавный доворот; carry-yaw тоже становится плавным. Сервер ставит rotation
  жёстко, как раньше.
- **`PublishNet` по изменению.** При стоянке `s/dir/dwelling/station` константны —
  запись в NetworkVariable не дёргаем (меньше сетевого шума, поведение то же).
- `0` в `_clientSmoothTime` = старое поведение (прямое применение `_netS`).

Что НЕ делали (сознательно, следующим итерациям):

- Не переносили кабинку в `FixedUpdate` на `MovePosition/MoveRotation` —
  уберёт опоздание зонда полностью, но это смена фазы движения + проверка
  порядка с `NetworkPlayer.Update`; отдельным тикетом после проверки этого.
- Не задавали `DefaultExecutionOrder` — та же причина (порядок Update между
  `ParomRoute` и `NetworkPlayer` сейчас не гарантирован; 1 кадр лага при
  гладкой дельте даёт константное отставание, а не джиттер).
- Не трогали общий carry (`NetworkPlayer`, `PlatformRideHelper`, `NpcBrain`) —
  он единый для кораблей/лифтов/парома и работает правильно.

## 4. T-PAROM-05: вертикальный баунс (телепорт коллайдера)

> Остаточный симптом после T-PAROM-04: лёгкое подпрыгивание при езде вверх/вниз.

**Причина.** `ApplyTrolley` писал `_trolley.position / rotation` напрямую в `Update`.
Кинематический коллайдер телепортировался: на подъёме крыша ящика
(`Box_cargo_Parom` в `WorldScene_0_0`) оказывалась внутри капсулы игрока,
и физика выталкивала райдера вверх; на спуске — зазор в 1 кадр и догоняющий
рывок carry. Сглаживание `s` этого не лечит — рвёт сам способ движения.

**Фикс (только паром, серверная симуляция не менялась).**
`ParomRoute.ApplyTrolley` больше не трогает трансформ — считает цель
(позиция + доворот) и отдаёт в `ParomTrolley.SetKinematicTarget`.
Кабинка едет в `FixedUpdate` через `Rigidbody.MovePosition / MoveRotation`:
контакт с `CharacterController` резолвится внутри физшага, без телепорта.
Дополнительно в `ParomTrolley.EnsurePhysics`:

- `interpolation = Interpolate` (опция `_interpolateRigidbody`) — гладкий рендер
  между физшагами;
- `sleepThreshold = 0` — стоящая на станции кабинка не засыпает и остаётся
  валидной платформой для `DetectGroundPlatform` (там `IsSleeping`-фильтр);
- первый кадр — снап к цели (кабинка не «доедет» с origin).

Откат: вернуть прямую запись в `ApplyTrolley` (одна строка, см. git).

## 5. Проверка (пользователь делает)

1. Console → 0 errors после `refresh_unity`.
2. Хост + 1 клиент. Клиентом встать на кабинку, проехать полный лег.
   Ожидаемо: на клиенте езда гладкая, ступеньки тик-рейта нет; на хосте —
   как было (точно). Отдельно проверить подъёмы/ложбины: вертикального
   баунса нет (T-PAROM-05).
3. Разворот на конечной (стоя на кабинке): плавный доворот вместо рывка.
4. F8/F9: кабинка на месте, тросы целы (FO-геометрия не менялась — якоря живые,
   кэши только длины, §4 из `00_PAROM_DESIGN.md` в силе).
5. Откат: `_clientSmoothTime = 0` возвращает поведение v1.
