## 1. Что на самом деле представляет собой «глобальный террейн» (факты проекта)

Всё измерено в редакторе на ассетах и на сцене, не «на глаз»:

| Факт | Значение |
|---|---|
| Объект | `WorldRoot_0_0/Terrain_0_0`, ровно три компонента: `Transform`, `Terrain`, `TerrainCollider` (никаких скриптов) |
| Трансформ | `m_LocalPosition: (0, 600, 0)`, поворот identity, `m_LocalScale: (1,1,1)` → **объектное пространство террейна совпадает с мировым по осям, высота = 600 м + локальная Y** |
| `TerrainData` | guid `196ca9d2684de5f4db5e95878bf42e80` (файл `Terrain_0_0_TerrainData (версия от 20.09.2026 13_47_38).asset`) — это именно тот вариант, на который ссылаются `Terrain` и `TerrainCollider`; два других ассета (`…13-47-38.asset`, `…13-47-38) (1).asset`) идентичны по содержимому и **сцене не нужны** (дубликаты, не удалялись) |
| Размер | `size = (80000, 4400, 80000)` м — согласован с `SceneID.SCENE_SIZE = 79999f` |
| Heightmap | `heightmapResolution = 1025` → **шаг сетки высот 78.125 м** |
| Альфамапа / basemap / detail | 256 / 1024 / 1024, `treeInstances = 0` |
| Диапазон высот | нормализованно 0.0288…1.0 → **126.9 … 4400 м над основанием террейна** (мир: 726.9 … 5000 м) |
| Слои террейна | два: `TerrainRock`, `TerrainSnow`; текстуры **4×4 px плейсхолдеры**, normal map нет, `tileSize = 4000×4000`, `metallic = 0`, `smoothness = 0` |
| Материал | `m_MaterialTemplate` → материал URP `TerrainLit` (guid `594ea882c5a793440b60ff72d896021e`), т.е. дефолт пайплайна |
| Настройки рендера террейна | `m_HeightmapPixelError: 200`, `m_SplatMapDistance: 20000`, `m_DrawHeightmap: 1`, **`m_DrawInstanced: 1`**, `m_ShadowCastingMode: 2` (двусторонний), `m_Holes` не используется |

Следствия для задачи:

1. **Авторской информации о цвете на террейне нет.** Раскраска сплатмапом пустая
   (4×4 px в слое — это «белый лист»), `alphamapResolution = 256` — то есть сейчас
   террейн и так рисуется процедурно-пустыми слоями. Процедурный материал ничего
   не «стирает»; вопрос не «можно ли», а «чем заменить пустоту».
2. **Ни один скрипт проекта материал террейна не назначает** (`materialTemplate` /
   `MaterialTemplate` — 0 совпадений в `Assets/_Project`). Назначение — ручное
   либо через `Terrain.materialTemplate`.
3. **Текстуры не нужны и UV не нужны** — согласуется с правилами каталога (`docs/Materials/README.md`, «Цель»).

## 2. ⚠ Блокирующий факт: `Draw Instanced` нельзя оставлять включённым

`Terrain_0_0` рисуется instanced-путём (`m_DrawInstanced: 1`). Что это значит для
самодельного шейдера — видно прямо в исходнике URP, который лежит в проекте:

`Library/PackageCache/com.unity.render-pipelines.universal@748d7458cc62/Shaders/Terrain/TerrainLitInput.hlsl:144-163`

```hlsl
void TerrainInstancing(inout float4 positionOS, inout float3 normal, inout float2 uv)
{
#ifdef UNITY_INSTANCING_ENABLED
    float2 patchVertex = positionOS.xy;
    float4 instanceData = UNITY_ACCESS_INSTANCED_PROP(Terrain, _TerrainPatchInstanceData);
    float2 sampleCoords = (patchVertex.xy + instanceData.xy) * instanceData.z;
    float height = UnpackHeightmap(_TerrainHeightmapTexture.Load(int3(sampleCoords, 0)));
    positionOS.xz = sampleCoords * _TerrainHeightmapScale.xz;
    positionOS.y  = height * _TerrainHeightmapScale.y;
#ifdef ENABLE_TERRAIN_PERPIXEL_NORMAL
    normal = float3(0, 1, 0);
#else
    normal = _TerrainNormalmapTexture.Load(int3(sampleCoords, 0)).rgb * 2 - 1;
#endif
    uv = sampleCoords * _TerrainHeightmapRecipSize.zw;
#endif
}
```

То есть на instanced-пути приходящие в вершинный шейдер `POSITION` и `NORMAL` — это
**координаты патча, а не геометрия террейна**; реальная высота и реальная нормаль
появляются только потому, что шейдер URP сам их подгружает из `_TerrainHeightmapTexture`
и `_TerrainNormalmapTexture` внутри `TerrainInstancing()`.
(`_TERRAIN_INSTANCED_PERPIXEL_NORMAL` в `TerrainLitBase.shader:77` — тот же механизм,
«Sample normal in pixel shader when doing instancing».)

ShaderGraph (URP Lit/Unlit target) не вызывает `TerrainInstancing` и не может —
он собирает вершинный стейдж сам.

**Вывод:** перед назначением процедурного материала тумблер `Draw Instanced`
на `Terrain_0_0` должен быть выключен (`m_DrawInstanced: 0`). Тогда террейн
рисуется обычным мешом со реальными позициями и нормалями, и работают ровно два
входа, которые нужны задаче: **высота вершины в метрах** и **нормаль поверхности**.

Цена решения: больше вершин на кадр (меш строится по heightmap с
`HeightmapPixelError = 200`), и `basemapDistance` перестаёт что-либо значить (§8).

Проверка «материал действительно лёг на геометрию, а не на плоские патчи» —
визуальная и за пользователем (**NOT RUN**). Если по каким-то причинам Draw Instanced
обязан остаться включённым, единственный рабочий путь — не ShaderGraph, а
рукописный `.shader`, который сам включает URP'шный `TerrainLitInput.hlsl` и вызывает
`TerrainInstancing()`; в стиле проекта (ProceduralSteel.shader) это возможно, но это
уже не нодовый материал из каталога.

## 3. Откуда берутся высота и уклон (и почему не из мирового Y)

**Зона = функция двух величин: высота (м) и уклон (°).**

| Величина | Как берётся в графе | Почему так |
|---|---|---|
| Высота | `Position` → Space = **Object** → `.Y` | На не-instanced меше local Y вершины = высота над основанием террейна **в метрах** (0…4400). Ровно то, что нужно для «чем выше — тем снежнее». Смещение 600 м из `m_LocalPosition` в это не входит и в пороги не подмешивается |
| Уклон | `Normal Vector` → Space = World → `Dot` с `(0,1,0)` → `acos` (или сравнение косинусов со `Smoothstep`) | Нормаль даёт широкие классы склонов (плоско/склон/обрыв), чего достаточно для зон; тангенсы и UV не нужны |

**Почему нельзя считать высоту из мирового Y.** Floating Origin двигает корни сцен по
**всем трём осям**:

- `Assets/_Project/Scripts/World/Core/FloatingOrigin.cs:128-135` — оффсет считается как
  `Mathf.Round` от позиции камеры **по X, Y и Z**, и мир сдвигается им целиком;
- новый контур — `Assets/_Project/Scripts/World/FloatingOrigin/OriginRebasePlan.cs:55-56, 99-100`:
  `translation = new Vector3(frame.Origin.X - origin.X, frame.Origin.Y - origin.Y, …)`.

Значит мировой Y — не стабильная «высота над уровнем», и после ребайза снеговая
граница уехала бы. Объектная Y к трансформу террейна инвариантна (ребайз двигает
корень, а не локальные вершины) — это ровно правило №1 каталога
(«База — object-space позиция»), и здесь оно получается бесплатно.

Террейн не повёрнут и не масштабирован (`m_LocalRotation` identity, `m_LocalScale` 1),
поэтому локальный «верх» = мировой «верх». Уклон берём по мировой нормали, чтобы
будущий наклон тайла не изменил картину; высоту — по объектной.

## 4. Зонирование: полосы и склон (калибровка по фактическому рельефу)

Пороги подобраны не наугад, а по гистограммам **этого** `TerrainData`
(1025² сэмплов, шаг 78.125 м):

Гистограмма высот (доля площади):

| высота, м | доля | накопительно ниже |
|---|---|---|
| 100–300 | 4.0 % | 4.0 % |
| 300–500 | 24.0 % | 28.0 % |
| **500–700** | **36.9 %** | **64.9 %** (ниже 600 м — 47.9 %) |
| 700–1000 | 14.1 % | 78.9 % |
| 1000–2000 | 16.3 % | 95.2 % (ниже 2000 м — 95.2 %) |
| 2000–3000 | 4.6 % | 99.75 % |
| 3000–4400 | 0.25 % | 100 % |

Уклон (по heightmap, центральные разности):

| диапазон | доля |
|---|---|
| 0–5° | 10.4 % |
| 5–10° | 21.7 % |
| **10–20°** | **38.7 %** |
| 20–30° | 18.8 % |
| 30–45° | 9.4 % |
| 45–60° | 0.97 % |
| >60° | 0.13 % |

Средний уклон по поясам: **< 700 м — 11.9°**, 700–2500 м — **23.5°**, > 2500 м — **29.9°**.

Отсюда рабочая раскладка (стартовые значения свойств; калибруются глазами пользователя):

| Зона | Высота, м над основанием | Уклон | Доля площади (по гистограмме) | Что это |
|---|---|---|---|---|
| Низина, зелёный слой (по лору — следы газа) | `_Low_Hi = 600`, перегиб `_Low_Soft = 120` | без гейта (0–15° практически везде) | ≈ 48 % | Плоское дно: зелень + жёлтые пятна, тонкая коричневая пыль |
| Скалы (основной слой) | 600 … 2000 | сюда же выдавливаются **все** склоны круче ~30° на любой высоте | ≈ 80 % вместе с низиной | Слоистая скала, трещины, блочность, осыпь |
| Снег | `_Snow_Low = 2000`, `_Snow_Soft = 250` | требуется плоскость: гейт `_Rock_Slope_Start = 26°` … `_Rock_Slope_Full = 38°` | ≈ 4.8 % (ниже 2000 м — 95 %) | Снег на полках и плечах, заструги |
| Лёд («ледяные вершины») | `_Ice_Low = 3200`, `_Ice_Soft = 200` | самый строгий гейт плоскости (≈ ≤ 20°) | ≈ 0.25 % | Вершинные ледники: стеклянный глянец, бледно-голубой |

**Порядок смешивания (зафиксирован, «склон побеждает высоту»):**

```
base            = Скала (snow = 0, ice = 0)
base            = Lerp(Скала → Низина,   HeightGate(low))            // высота, без склона
base            = Lerp(base  → Снег,     HeightGate(snow) × FlatGate) // высота × плоскость
base            = Lerp(base  → Лёд,      HeightGate(ice)  × FlatGateStrict)
```

`FlatGate = 0` на крутых гранях → **камень проступает на склонах при любой высоте**,
включая вершины; лёд и снег остаются только на пологих полках. Это и есть заказанное
«на склонах просвечивал камень». Средний уклон > 2500 м (29.9°) при пороге 26–38°
гарантирует, что пики читаются скальными, а снег ложится пятнами.

**Обязательная деталь:** пороги обязаны шуметь. Ровный `Smoothstep` по одной высоте
даёт идеальную горизонтальную линию раздела — на 80 км это выглядит как разлиновка.
Границы смещаются крупным fbm (`_Zone_Warp`, десятки метров по высоте, сотни метров
по XZ), т.е. `Threshold = _Snow_Low + _Zone_Warp · PCTrn_FbmBands(p) − _Zone_Warp · 0.5`.

## 5. Слои рисунка

Все слои — процедурные, без UV и без текстур (правило каталога). Разделение по каналам:

| Слой | Куда влияет | Назначение |
|---|---|---|
| `PCTrn_RockStrata` — ridged fbm, вытянутый по объектной Y | альбедо + height | Слоистость/плитчатость скалы |
| `PCTrn_RockCracks` — distance-to-ridge с домен-warp + маска-пятно | альбедо (тёмное) + height (вниз) | Расщелины и разломы |
| `PCTrn_RockBlocks` — Worley: F2 − F1 + тон ячейки | альбедо (тон блока) + height | Блочность массива, «поле обломков» |
| `PCTrn_Scree` — мелкий Worley + fbm «наклонной» маской | альбедо + height | Осыпь/щебень на пологих |
| `PCTrn_SnowDrift` — fbm, растянутый по XZ, порог накопления | альбедо (пятно) + height (мягко) | Заструги, нанос на плоскостях |
| `PCTrn_IceCracks` — Worley-edges | альбедо (тонкие тёмные линии) + height (мелко) | Трещины льда |
| `PCTrn_LowMottle` — крупный fbm + пятна | альбедо | Зелёная низина: разнотон, жёлтые проплешины, следы «газа» |
| `PCTrn_Dust` — fbm с гейтом «плоско» | альбедо (обеление/пыль) | Пыль на пологих, глобальный верхний слой |

Прочее по каналам PBR:

- `Smoothness`: лёд ≈ 0.90 (самое глянцевое), снег ≈ 0.35, скала ≈ 0.10–0.15 (мат), зелёная низина ≈ 0.25 + пятна. Скала полируется к кромкам блоков (узкая полоса).
- `Metallic` — **не подключается** (ландшафт — диэлектрик), как в Concrete/Cobble/Bark.
- `Emission` — не подключается.
- `Occlusion` — можно отдать грубому fbm-затемнению расщелин; не обязательно.
- Палитра — старт: `_Rock_Color` ≈ (0.30, 0.29, 0.27), `_Rock_Deep_Color` ≈ (0.14, 0.13, 0.12), `_Snow_Color` ≈ (0.92, 0.94, 0.97), `_Ice_Color` ≈ (0.78, 0.87, 0.94), `_Low_Green_Color` ≈ (0.24, 0.35, 0.20), `_Dust_Color` ≈ (0.45, 0.43, 0.38).

## 6. Домен шума: главное отличие от всех прежних материалов

У пропсов объектные координаты — единицы. У террейна 80000×80000 м, то есть
шум считается на величинах до **80000**. Что из этого следует:

1. **Хеш обязан быть без `sin`.** В проекте уже принят Hoskins-стиль
   (`ProceduralGlassNoise.hlsl:11-16`: `p = frac(p * 0.1031); p += dot(p, p.zyx + 31.32); …`) —
   он приводит аргумент в 0…1 первым `frac`, поэтому на 80 км квант хеша остаётся
   порядка миллиметров (оценка по мантиссе float: при 80000 м ε ≈ 0.0078 м, после
   деления на 0.1031 — доли метра, в масштабе шума — мм). Классический
   `frac(sin(dot(p, k)) * 43758)` на таких координатах деградирует в полосы,
   поэтому **sin-based хеш здесь запрещён**. Повторять механику
   `PCGlass_*`/`PCConc_*` (тот же стиль, свой префикс `PCTrn_`).
2. **Масштаб шума задаётся в метрах.** `_Noise_Scale` трактуется как «клетка в метрах»
   (`p = PosObject.xz / _Rock_Cell`), а не как у пропсов. Это же даёт бесплатную
   независимость детализации от размера террейна.
3. **Домен заворачивается.** Для октав с высоким `freq` аргумент растёт быстрее всего;
   безопасный приём — `fmod` с периодом (`_Domain_Repeat`, кратный масштабу, старт
   ≈ 4096 м) плюс крупный «разрывной» fbm, маскирующий повтор. Если заворот не
   вводить, смотреть за полосностью на дальних углах террейна (визуальная проверка, пользователь).
4. **Детализация гасится расстоянием.** Правило каталога №5 (Near/Far) здесь критично:
   80 км поверхности в экранном пространстве — это шум, который физически не может
   быть мелким везде. Дальняя половина террейна обязана ехать на «Far» (1 октава, без bump).

## 7. Рельеф (bump): проектная ловушка и её обход

1. **Рельеф не может прийти от геометрии.** Шаг сетки высот 78.125 м при
   `HeightmapPixelError: 200` — это очень грубый меш: ни камней, ни трещин в вершинах нет.
   Вся мелкая форма — только шейдер.
2. **Слот `Strength` у `Normal From Height` должен быть подключён к свойству**
   (`_Bump_Strength`), иначе материал получит шаблонный дефолт **0.01** и рельеф
   будет погашен ×100. Это ровно та «Известная ошибка сборки», которая уже ловилась
   в Cobble/Bark/Concrete/Plastic (разбор — `docs/Materials/README.md`, раздел
   «Известная ошибка сборки: рельеф…»); Brick/Plate/Parquet — эталоны лечения.
   Обязательная проверка после сборки: слоты `NormalFromHeightNode`
   `In = 0, Strength = 2, Out = 1`; в сгенерированном шейдере
   `Unity_NormalFromHeight_Tangent_float(` со **свойством** вторым аргументом
   (не `float(0.01)`); `surface.NormalTS = _NormalFromHeight_…_Out_1_Vector3;`.
3. **NFH — производная по экрану.** На поверхности в 80 км это гарантированный
   алиасинг вдали: рельеф обязан гаснуть по расстоянию/высоте (`_Bump_Fade_Start/End`)
   и жить в полную силу только в Near-пресете.
4. Коэффициенты высоты раздельные по видам (`_Rock_Bump`, `_Crack_Bump`, `_Snow_Bump`,
   `_Ice_Bump`), как в Wood v2.1 / Brick / Tiles — общий `_Bump_Strength` остаётся
   только силой, а не амплитудой конкретного слоя.

## 8. Что остаётся неизменным и что проверить отдельно

| Подсистема | Зависимость от материала |
|---|---|
| `TerrainCollider`, физика, `Physics.Raycast` по террейну | нет — материал не влияет; коллайдер берёт heightmap |
| `PeakRegistry.cs` (сэмплит heightmap террейна для пиков NPC-кораблей) | нет — читает `TerrainData`, не шейдер |
| `ViewDistanceApplier.cs` (ищет по имени `Terrain_0_0`, владеет `heightmapPixelError`/`basemapDistance`) | нет, но **`basemapDistance`/`m_SplatMapDistance: 20000` теряет смысл**: запечённая basemap семплится только шейдером TerrainLit; кастомный материал её не читает, и «замыливания» вдали не будет. `heightmapPixelError` продолжает работать (это LOD меша) |
| Два `TerrainLayer` (`TerrainRock`, `TerrainSnow`) и `alphamapResolution: 256` | остаются в ассете, но не читаются. Это не мусор: альфамапа доступна как **опциональный канал ручной правки** (например «зелень только в этой котловине») без смены шейдера |
