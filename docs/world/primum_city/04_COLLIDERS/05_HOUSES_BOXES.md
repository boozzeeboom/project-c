## 1. Что сделано и чем это отличается от предыдущей попытки

| | Попытка «точные меши» (`0045cb72` → `21981060`) | **Сейчас: боксы** |
|---|---|---|
| Что в физике | 100 `MeshCollider` из RAW, 1 379 458 тр. | 10 355 `BoxCollider` |
| Двери | Настоящие проёмы в меше, но проём **не гарантирован** — дырка в меше есть, прохода может не быть | Проём **вырезается** из бокса стены по окну двери: лево / право / над |
| Игрок | «Точные, но множество дыр; толкает в стену между коллайдерами, из которой не выйти» | Один бокс на прогон стены — щели между кусками кладки исчезли как класс |
| Стоимость | 570k → 1.38M треугольников на кук | ~10.4k боксов, ноль треугольников |
| Классификация | по имени + геометрическое «угадывание» | **только по имени**, узкий белый список |

**Почему отказались от мешей.** Меш из RAW повторяет модель вместе с её болезнями: кладка собрана из
десятков объектов, между ними щели; булевы вырезы не делались; а «дыр» в модели столько, что игрок
цеплялся за стыки. Бокс по прогону стены — наоборот: он **не может** иметь щели внутри прогона.

**Почему «только по имени».** Геометрические правила прошлого поколения (`bbox-plate`, `F<этаж> → плита`)
превращали в коллайдеры весь реквизит этажа (`F0_BILLIARD_BODY`, `FURN_2_BED`, `C1_LIFE_CAB`) — игрок
не мог пройти ни в одном доме. Пропустить объект **дешевле**, чем заварить проход.

## 4. Правила отбора (генератор)

### 4.1 Словари видов (`strict_class`, только по имени)

```
WALL_KIND = WALL, WALLS, SHELL, PART, PARTITION(S), BACKWALL, WA, INTWA, W2, ZX, MURO, STENA
SLAB_KIND = SLAB, FLOOR(S), ATTIC, PLATE, MEZZ(ANINE), GALLERY, VER, VERANDA, PORCH, PLATFORM, BASEPLATE
ROOF_KIND = ROOF(S), PARAPET, GABLE, HIP, HIPGABLE, MANSARD, TENT, CORNICE
STAIR_KIND = STAIR(S), STAIRCASE, STEPS, STAIRTREAD, FLIGHT, STFLIGHT, PORCHST
ARCH_KIND = ARCH, ARCADE, PASSAGE, PASS, PORTAL
```

`VETO` (~150 токенов) — окна/столярка, двери/фурнитура, мебель, текстиль, перила/балясины,
инженерия, кровельные причиндалы. Проверяется и по сырым, и по очищенным от цифр токенам.
`DOOR_VETO` отдельно отсеивает «двери»-мебель и «двери»-окна, а также **`FRAME` / `SILL` / `TRANSOM`**:
у одной двери наличник и подоконник давали вторую запись проёма (1.68 м) поверх уже найденной створки
(1.31 м) — на ADMIN это дало −125 дублей (`205 → 80`).

**Геометрический запасной вариант** — только для однозначных форм и без слов-вето:
`dz ≥ 2.0 ∧ min(dx,dy) ≤ 0.40 ∧ max(dx,dy) ≥ 2.0` → `WALL`; `dz ≤ 0.45 ∧ dx ≥ 2.0 ∧ dy ≥ 2.0` → `SLAB`.
Двухмысленные «кубы» (тумбы, памятники) **не берём**.

### 4.3 Стена: плоскости → прогоны → вычитание проёмов

1. Все стены дома проецируются на главную ось дома (`principal_theta`).
2. Раскладываются по **плоскостям**: у каждой берётся главная ось (вдоль/поперёк), смещение
   кластеризуется с `PLANE_TOL`.
3. Плоскость режется на **прогоны** по `RUN_GAP`.
4. Прогон × его высота = прямоугольник; из него вычитаются **окна проёмов** (`rect_subtract`),
   результат — боксы лево / право / над дверью.
5. Прогон с `(t1 − t0) > 1.00` **выбрасывается** (`run_thick`) — слиплись разные плоскости, бокс-блоб не нужен.

### 4.4 Проём — одно окно на дверь, а не дырка в прогоне

Ключевое решение. Дверь в модели — это **десяток объектов** (`_DOOR_1_JAMB_L`, `_HEAD`, `_HINGE1`,
`_GRIP`, `_LEAF_PAN_*`): на 620 домов приходится **15 836** дверных объектов.

```
door_windows(doors, arches, th):
  along_u = (pu1-pu0) >= (pv1-pv0)                 # полотно тянется вдоль прогона
  w = max(span, MIN_CLEAR_W), центрируется по середине полотна
  толщина: t0/t1 расширяются на PLANE_REACH (1.00 м) в обе стороны
  z:   arch  → bb[4] .. bb[4] + CLEAR_H
       door  → bb[5] − CLEAR_H .. bb[5]            # от ВЕРХА полотна вниз
       PORTAL в имени → bb[4] .. bb[5]             # на ВСЮ высоту объекта, в склейке не участвует
  склейка частей: одна ориентация ∧ полосы толщины пересекаются ∧
                  зазор ≤ DOOR_JOIN ∧ ширина после склейки ≤ DOOR_MAX
```

Запись проёма (`doors[]` в JSON) — **центр окна**, а не центр обрезанного куска прогона. Это то,
что делает проверку проходимости (363/364) осмысленной.

### 4.5 Перекрытия, крыши, марши

* **Перекрытия:** объекты класса `SLAB`; отбрасывается всё толще 0.90 м (`slab_thick`) и мельче
  `max(4.0 м², 0.20 × самая крупная плита дома)` (`slab_small`). Уровни по верхней грани,
  слияние с `LEVEL_Z` → **один бокс на уровень**.
* **Плита с дырками (`plate_boxes`)**: если в группе дома ровно **один** плитный объект, его габарит
  накрывается сеткой `PLATE_STEP`, из каждой ячейки пускается луч сверху вниз; маска «есть материал»
  эродируется на `PLATE_ERODE` и покрывается максимальными прямоугольниками (`greedy_rects`) →
  несколько боксов с `th = 0.0`. Пустая доля < `PLATE_HOLE_SHARE` — плита остаётся одним боксом.
  **Плита с дырками никогда не выпускается одним боксом по габариту** — иначе завариваются
  лестничные клетки, атриум и библиотечный void. На ADMIN: 14 плит → 132 бокса.
* **Крыши:** объект `ROOF` → один бокс на полосу высот (слияние 1.8 м), минимум 0.25 м толщины.
  Если у группы нет объекта крыши — синтезируется по габариту стен (`synth_roof`), и берётся
  **только самая верхняя полоса**: группа ADMIN разбита по этажам (`ADM_F1_WALL`, `ADM_CORR_F2`,
  `ADM_WC_F3`…), и верх группы — это потолок этажа, а не крыша дома. Замер 24.10: 42 таких
  бокса, по одному 68 × 64 м на **каждом** этаже.
* **Синтетическая крыша под настоящей плитой выбрасывается:** если сверху есть плита, низ которой
  садится на верх синтетического бокса (−0.05…+0.60 м), бокс лишний — плита уже закрывает верх
  группы и при этом **вырезана по проёмам**. Без этого правила бокс 68 × 64 на 28.89 м садился в
  проём шахты настоящей плиты F2 (29.16…29.56) и обрывал марш библиотеки за 0.4 м до площадки,
  а бокс на 41.73 м закрывал выход на кровлю.
* **Марши — побъектно, без кластеризации.** Замер 22.10: кластеризация по касанию габаритов
  склеивала A + B + LAND + PODIUM в **один** бокс — уклон 12.6°, подъём 1.86 м вместо 4.00,
  низ на 1.25 м выше пола: лестница физически непроходима. Сейчас на каждый объект:
  1. `dz < 0.60` ∨ `min(dx,dy) ≤ 1.60` ∨ **вершин < 12** → сплошной бокс (`stair_flat`);
  2. сверху есть масса (низ в пределах 0.30 м от верха объекта ∧ перехлёст в плане 0.10 м) →
     сплошной бокс: это опора ПОД летом, а не второй марш;
  3. иначе — **наклонный бокс от своего `bb[4]` до своего `bb[5]`**, а **ось хода берётся
     ЗАМЕРОМ**: по габариту сеткой `STAIR_PROBE_STEP` пускаются лучи сверху вниз,
     МНК-плоскость верха даёт градиент `(A, B)` → ось `atan2(B, A)` и уклон `hypot(A, B)`.
     Низ/верх бокса — по-прежнему `bb[4]`/`bb[5]`: они совпадают с плитой и площадкой.
  **Ось НЕЛЬЗЯ брать по длинной стороне габарита.** Замер 25.10: главные марши ADMIN —
  `3.60 × 4.00` при ходе вдоль **3.60**, то есть длинная сторона поперёк хода; выбор «по длинной
  стороне» поворачивал диагональ на 90° (28 боксов, из них 8 главных маршей шли поперёк ступеней,
  уклон верхней огибающей `a = 0.000`, подъём 2.14 м на 4.00 м чужой оси). Настоящая геометрия
  ступеней при этом ИЗМЕРИМА: плоскость верха ложится со СКО 0.036…0.047 м, уклон 27…33°.
  Проверка после правки: 14 наклонных боксов против меша ступеней — максимальное отклонение
  поверхности **0.131 м**, разрывов опоры внизу/вверху — 0.
  Площадки, подиумы и ступени (8 вершин, плоский верх) дают `hypot(A, B) = 0` и остаются сплошными боксами.
* **Плита и крыша режутся по пятну марша** (`carve_plates_by_stairs`): где марш выходит сквозь
  плиту, а дыры в ней нет (крыло — 1.3 м марша под плитой F2; главная — последний марш сквозь
  синтетическую крышу), плита делится на до 4 прямоугольников вокруг пятна марша (+0.12 м).

### 4.6 Система координат

```
world → local:  s = C + (p − C) · K      C = (7.5, −148.0, 18.5)   K = 1.07
                local = (−s.x, s.z, −s.y)
aabb           = (x0, x1, y0, y1, z0, z1)   →  bb[5] = верх, bb[4] = низ
```

Отображение зеркальное (det = −1) — поэтому OBJ-эпоха писала треугольники в обратном порядке.
Для боксов важно другое: **линейная часть** `mdir(v) = (−v.x, v.z, −v.y)` — ею пересчитываются
направления. `make_box` складывает ±180° → 0, а 90/270° → 0 с перестановкой X/Z.

## 5. Что делает Unity-билдер

* Читает `houses_boxes.json` (классы `RootDto/ChunkDto/BoxDto/DoorDto`) — **больше ничего не читает**,
  CSV/OBJ эпохи мешей ему не нужны.
* Группы на чанк: `HOUSE_WALL_BOX`, `HOUSE_FLOOR_BOX`, `HOUSE_ROOF_BOX`, `HOUSE_STAIR_BOX`.
* **Осевые боксы** лежат на одном объекте группы (по `BoxCollider` на бокс) — это убирает 10 тысяч
  лишних трансформов. **Повёрнутые и наклонные** — детьми `R/rN`.
* Трансформ объектов — **identity**: координаты уже в пространстве корня `PRIMUM_COLLIDERS`, который
  копирует трансформ `PRIMUM` и **едет вместе с ребейзом мира**.
* Слой `PRIMUM` (8), static-флаги **не ставим** (Floating Origin).
* `Physics.SyncTransforms()` + `EditorSceneManager.MarkSceneDirty()` после сборки.

### 7.1 Что НЕ надо «чинить» заново

* `VETO` уже содержит перила/балясины/поручни, сантехнику, навершия, плинты, желоба, мебель, окна,

* `PrimumCollidersBuilder` (меню 340–342) дома больше не строит; трогать его ради домов не нужно.

## 8. Открытые дефекты (измерены, не исправлены — «хорошо, не идеально»)

### 8.1 `FLOOR = 2158` из 3 459 занятых проходов — **главный остаток**

`s` `build_slabs()` выдаёт **один бокс на уровень** по объединению габаритов всех плит уровня.
В `S1_GLD_P1_25H` такой бокс имеет размер **7.7 × 0.30 × 60.4 м** и висит на **0.71 м выше порога**
десятков проёмов нижнего уровня — он их и запирает.

Почему так: уровень сливается по верхней грани (`LEVEL_Z = 0.35`), а габарит берётся по **union**
всех плит уровня. Для одного этажа это правильно и экономно; но галерея/веранда соседнего уровня
попадает в тот же бокс и накрывает проёмы под собой.

**Кандидат на исправление:** резать плиту уровня не по union, а по **связным компонентам**
(как `build_stairs` кластеризует марши) — тогда галерея получит свой бокс. Проверять тем же меню 364:
цель — `FLOOR` в разряде сотен, а не 2 158.

### 8.2 6 «лишних» `MeshCollider` `STAIRS` в чанках домов

В 6 из 25 чанков (`S2_TRD_P1_28H`, `S3_TRD_P2_26H`, `S3_TRD-ES_P1_37H`, `S4_TRD_P3_26H`,
`S9_TRD-N_P1_28H`, `S9_TRD-S_P1_16H`) остались группы `STAIRS` с `PM_STAIRS_*` — наследство меш-эпохи.
В `ObsoleteGroups` они **не входят** (там только `HOUSE_*`), `RemoveLegacyBoxes()` их не трогает.
Решение (удалять или оставить как страховку маршей) — за заказчиком.

### 8.3 `WALL = 109` — последние заваренные стенами проёмы

109 из 6 140 (1.8 %). Это по большей части:
* прогоны, где проём не попал в полосу `PLANE_REACH`, потому что полотно лежит в другой
  плоскости дома (L-образные и угловые входы);
* 193 проёма шире 1.65 м, из которых **156 шире 5 м** — объекты-колоннады (`MASS_PORTAL_*` в `S1_GLD`,
  `RES_RG_*` в `S9_RING`), где один «дверной» объект — фасад целиком. Абсолютный максимум
  **51.85 м** — `RES_RG_E_29_DOOR_HARD`. Такие записи нужно **исключать** из `doors[]`
  (они не проход, а портал/терраса), а не расширять под них проём.

### 8.4 324 «блобообразных» стен-бокса и 157 боксов выше 8 м

Фильтр `wall-blob` работает на уровне **объекта**, а эта форма возникает на уровне **прогона**
(склейка нескольких coplanar-объектов в один прямоугольник). Отдельный случай — тонкие высокие
прогоны галерей и аркад (`0,5 × 11,1 × 45,5`). Гейта по форме прогона (высота/аспект) пока нет.
Кандидат: после `split_runs` резать прогон по этажам — этаж уже есть **в имени** объекта
(`RES_S2_02_0_WALL_E_00` → `_0_`/`_1_`).

### 8.5 1 145 проёмов «без пола под ногами»

Луч вниз 3 м от центра проёма не находит коллайдера под `PRIMUM_COLLIDERS`. Причина не в боксах:
это проёмы, чей пол — улица/терраса вне узла, либо проём на уровне выше/ниже записанного порога.
Доля выросла (262 → 1 145) после перехода с «дырка в прогоне» на «окно на дверь» — набор стал строже.

На ADMIN та же проверка даёт **0 из 80** — но только после переноса пробы под порог
(`w.y − d.h*0.5 + 0.42`). Пока проба стояла в середине объёма, она выдавала 40 «без пола» на чистой
сцене: луч начинался внутри плиты. При перепроверке «без пола» сначала убеждайтесь, что число
получено текущей сборкой кода, а не прошлым прогоном.

### 8.6 Закрытые створки `PRIMUM_DOORS` (0.52 × 2.30 × 0.07)

Полотно блокирует проём, пока дверь закрыта — механизма открытия нет. Это **не** дефект боксов:
если игрока вдавливает в стену при открытии, правильный шаг — перевести бокс полотна в
кинематический триггер, а проём закрывать отдельным объёмным боксом.

## 10. Жёсткие правила (не нарушать)

1. **Дома — боксы.** Один бокс на прогон стены, один на уровень перекрытия, один на полосу крыши,
   один наклонный на марш. Никаких мешей для домов.
2. **Мебель, окна, стекло, столярка, декор — никогда не попадают в физику.** Классификация
   **только по имени**, никогда по коллекции.
3. **Проём не выводится из габарита полотна** и **не** из низа двери: ширина ≥ `MIN_CLEAR_W` по
   центру полотна, высота `CLEAR_H` вниз от **верха** полотна.
4. **Склейка частей двери ограничена**: `DOOR_JOIN = 0.20`, `DOOR_MAX = 1.60`. Иначе колоннада
   становится одним проёмом.
5. **Проём — окно в осях дома**, режущее все параллельные плоскости в `PLANE_REACH`, а не
   вырез в одном прогоне.
6. **Трансформы — identity**, слой 8, static-флаги **не ставим** (Floating Origin).
7. **RAW не менять** — только чтение.
8. **Плита с дырками никогда не выпускается одним боксом по габариту** — только `plate_boxes()`,
   и смещение ошибки всегда в сторону меньшей плиты.
9. **`WALL_BLOB_T` не опускать к 0.60** — типовая стена ADMIN ровно 0.60 м.
10. **Play Mode запускает пользователь.** Численные проверки — меню 363/364/367/368 и `tools/*.py`.
