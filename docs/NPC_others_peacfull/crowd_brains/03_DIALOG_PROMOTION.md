# 03 — Промоут на разговор: «поговорил → герой (на день)»

> Механика: игрок может заговорить с любым видимым. Сервер выдаёт ему диалоговую лизу из пула: сессия + дерево + квест-экшены. Закрыл диалог — «геройство» остывает по TTL («на день» = длинная лиза без тика, см. `01 §1.5`).

## 3.1 Почему это уже наполовину работает у нас

Разговорный тракт изначально спроектирован без `NetworkObject` на NPC:

- `NpcController` (`Assets/_Project/Quests/NpcController.cs`) — обычный `MonoBehaviour` + триггер. Не сетевой. Регистрируется в статическом `Registry[npcId]`, отдаёт `IsWithinDistance`.
- `QuestServer.RequestTalkToNpcRpc(npcId, treeIdHint)` (`Quests/Network/QuestServer.cs:491–568`): проверяет рейт-лимит → находит `NpcController.Find(npcId)` → проверяет дистанцию (`IsWithinDistance`, иначе reject «too far») → ищет `questDatabase.GetNpc(npcId)` → берёт `defaultDialogTree` или строит **runtime-fallback** (`GetOrBuildFallbackTree` из `questOffers/questTurnIns/greetingText`, `QuestServer.cs:540–544`) → открывает серверную сессию `QuestWorld.OpenDialog(clientId, npcId, tree)` → шлёт `DialogStepDto` → `MarkNpcTalked` + `TalkedToNpcTrigger`.
- Дальше `RequestAdvanceDialogueRpc` (`QuestServer.cs:575–664`) валидирует сессию (`session.npcId == talkingToNpcId`), условия рёбер, фаерит `DialogueAction`, публикует `DialogVisitedEvent`, двигает `currentNodeId`.

Вывод: **«поговорить» = `npcId` + позиция + дефиниция/дерево + сессия.** Ничего из этого не требует тела с `NetworkTransform`. Толпе не хватает только трёх вещей: (а) стабильного `npcId` для каждого видимого, (б) резолвера `npcId → позиция/дефиниция` для толпы, (в) пула сессий/лиз с TTL. Всё остальное — reuse.

## 3.2 Сущности разговора

- **CrowdNpcId.** Каждому слоту толпы назначается стабильный `npcId` вида `cr_<zone>_<index>` (например, `cr_gigant_deckB_042`). Стабильность — ключ: по нему живут отношение (`NpcAttitude`), `TalkedToNpc`-флаги, квест-офферы, «герой-на-день». Сид внешности/имя/фракция/профессия генерируются детерминированно из `npcId` (один и тот же докер — один и тот же человек при каждом заходе, пока не убит/не ротирован).
- **CrowdNpcResolver (сервер).** Аналог `NpcController.Find` для толпы: `npcId → {позиция (якорь+смещение), interactionRadius, NpcDefinition-подобное}`. Позиция — грубая (якорь), её достаточно для `IsWithinDistance`-проверки с тем же допуском, что в `02 §2.2`.
- **CrowdDefinition (данные, не SO на каждого).** Полноценный `NpcDefinition`-ассет на каждого из тысячи — ад для дизайнеров (тот же анти-паттерн, что «каждый NPC — unique prefab» из `npc_ship/02 §9`). Вместо этого: **профиль-шаблон + именная дельта.** Шаблоны: `докер / пассажир / торговец-лоточник / страж / механик / фермер...` (5–10 SO). Дельта на `crowdId`: имя, сид внешности, фракция, `greetingText`, 0–2 `questOffers`, `services`-маска (Trade/Repair/... из `NpcDefinition.cs:44–53`). Именные герои — полноценные SO как сейчас.
- **DialogPool (сессии).** Сессии `QuestWorld` уже идут по `clientId` (1 диалог на игрока одновременно — см. stale-session close в `QuestServer.cs:514–518`). Пул здесь = **кап одновременных героев-разговорников на зону + лизы «остывания».** Стартовая гипотеза: 1 активный диалог на игрока (как сейчас) + до 4–6 «тёплых» лиз на зону (недавно говорили, быстро возобновляются без полного резолва).
- **TalkLease.** `{crowdId, clientId, sessionRef, expiresAt, heroUntil}`. `expiresAt` — активная сессия (секунды/минуты), `heroUntil` — «герой на день» (часы, игровые). Пока жива сессия — дерево/экшены/валидация. Пока жив `heroUntil` — приоритет в клиентском пуле, именной бейдж, быстрый резолв, непротухающая обида/память.

## 3.3 Пошаговый сценарий «E на толпе»

```
0. Было: визуал cr_gigant_deckB_042 стоит на якоре, сервер знает ростер-запись.
1. Клиент: E в радиусе → RequestTalkToNpcRpc("cr_gigant_deckB_042", null)
   (тот же RPC, что для именных — отдельный не нужен).
2. Сервер Validate:
   - рейт-лимит (как сейчас, maxOpsPerMinute);
   - резолв позиции через CrowdNpcResolver (вместо NpcController.Find);
   - дистанция IsWithinDistance с допуском толпы; иначе reject (античит «говорю с города»);
   - занят ли игрок другой сессией (stale-close как сейчас);
   - занят ли crowdId диалогом с другим игроком → вежливый отказ «он занят»
     (не баг: два игрока не должны двигать один currentNodeId).
3. Сервер Admit: есть ли слот DialogPool на зону? Нет → отказ с причиной
   (клиент показывает «отмахнулся, некогда» — фолбэк, не лаг).
4. Сервер Bind:
   - собрать дефиницию: шаблон + дельта ростера (+ heroUntil-дерево, если «герой на день»);
   - дерево: именное defaultDialogTree (если есть) → иначе fallback из
     greeting+questOffers/turnIns (тот же GetOrBuildFallbackTree);
   - OpenDialog(clientId, npcId, tree) + TalkLease{ttl сессии}.
5. Диалог идёт обычным трактом: BuildDialogStep → DialogStepDto → Advance →
   условия → DialogueAction (Offer/TurnIn/OpenMarket/Reputation/...) → DialogVisitedEvent.
   Никакой отдельной «толпо-диалоговой» системы.
6. Закрытие (ESC/конец/уход): CloseDialog + TalkLease.expiresAt = now + grace
   (5–10 минут «тёплый»), heroUntil = now + «день» (если был содержательный разговор:
   квест взят/сдан, отношение изменилось, игрок выбрал именную ветку — см. §3.4).
7. Итог в ростер: attitudeDelta, talkedFlag, questFlag, heroUntil, lastTopicSeed.
   HERO_DOWN наблюдателям (бейдж «знакомый» остаётся на клиенте).
```

## 3.4 Когда толпа становится «героем на день», а когда — нет

Не каждый «привет» достоин длинной лизы (иначе через неделю героями-на-день будут все 100500). Правила повышения до `heroUntil`:

- **Да:** взят/сдан квест, куплено/починено через `services` (Trade/Repair — уже есть в `NpcDefinition.services`), отношение пересекло порог (`hostilityThreshold`-механика из `NpcBrain.cs:110`), игрок дал имя/запомнил (спец-реплика), скрипт назначил (квест требует «найди докера 042»).
- **Нет:** пустой greeting без ветвления, отказ по условиям рёбер, разговор прерван уходом в первые 2 реплики.

«Герой на день» даёт (без серверного тика!): именной показ (имя вместо «Докер»), приоритетный слот в клиентском пуле видимых (не вытесняется), быстрый резолв (кэш дефиниции), доступ к именному дереву при повторном подходе, непротухание обиды/памяти до конца лизы, возможность скриптов найти его (`Find(heroId)`). Не даёт: постоянного тика, охраны, квестовой неуязвимости (если не положено).

## 3.5 Деревья для тысяч: генерация, а не авторство

Писать дерево на каждого докера — невозможно и не нужно. Лестница:

1. **Greeting + 1–2 оффера** (fallback-генератор, уже есть прецедент `GetOrBuildFallbackTree`): «Привет. Работы нет, а вот <questOffer> — к боцману». Покрывает 80% толпы.
2. **Шаблонные деревья по профессиям** (5–10 `DialogTree`-ассетов): докер/страж/торговец/пассажир/механик. Ветки параметризуются `npcId`-дельтой (имя, ставка, слух-сид). Покрывают 15%.
3. **Именные деревья** — только героям по должности + героям-на-день по назначению скрипта. Покрывают 5%, но дают 90% сюжета.

Слухи/сплетни — отдельный дешёвый контент: пул одноразовых реплик по `lastTopicSeed` + состоянию мира (шторм, цены через `TradeWorld`-хуки как в `npc_ship/03 §6.2`, прибытие «Гиганта»). Слух не требует сессии после первой выдачи — только флаг «слышал».

## 3.6 Конфликты и гонки (честно)

- **Двое говорят с одним.** Сессия одна на `clientId`, но дерево одно на `npcId`. Решение: лок сессии на `crowdId` (первый занял — второй получил «занят, подожди»). Долгих очередей нет — отказ вежливый.
- **Бьют того, с кем говорят.** Боевая лиза старше диалоговой: диалог прерывается (`CloseDialog` + реплика «потом!»), слот переходит бою. Добивать собеседника — можно, с репутационными последствиями (`-20` как в `NpcBrain.OnNpcDeath`, + `surrendered`-штраф если сдался).
- **Герой-на-день убит.** `heroUntil` сгорает, квесты с него — в состояние «провален/переназначен» по правилам квестов (не придумывать здесь, сослаться на квестовый дизайн). Визуал — заменён новым сидом («другой докер»), старый `npcId` — в архив.
- **Игрок ушёл из AOI посреди диалога.** Сессия закрывается по таймауту, `heroUntil` сохраняется (вернулся — продолжил как со знакомым).

## 3.7 Корабельная специфика

- Разговор на движущейся палубе — в локальном кадре корабля (та же причина, что в `02 §2.8`). Дистанция `IsWithinDistance` считается в ship-local, иначе качка/ребейз будут рвать сессии.
- Шум палубы: `interactionRadius` меньше (2.0–2.5м), очередь не собирается — отказ вместо толкучки.
- Вахта/смена: дом-якорь + расписание (см. `04`) важнее, чем в городе: «механика 042 сейчас на вахте у слота 7, после смены — в кубрике». Герой-на-день ходит по расписанию, а не стоит вечно.
