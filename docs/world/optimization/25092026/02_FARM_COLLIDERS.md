# Коллайдеры фермы и пилы зон — что / почему / как (T-PERF02, пункт «ц»)

## Что есть сейчас (факты)

- Подсчёт по файлу `Assets/_Project/Scenes/World/WorldScene_0_0.unity`:
  **BoxCollider — 9 712**, MeshCollider — 6, SphereCollider — 34, CapsuleCollider — 9.
- То есть ферма (и окружение Примума) — это тысячи лоуполи-объектов, у каждого свой
  первичный коллайдер-бокс, сгенерированный по мешу. Нагрузку при создании не проверяли.
- Потребители: `OuterCommZone.PollPlayersInRange/PollShipsInRange`
  (`Scripts/Docking/Zones/OuterCommZone.cs:227,267`) — `Physics.OverlapSphere(pos, 1000м,
  ~0 /* все слои */, Ignore)` каждые 0.25 с с каждого из 10 экземпляров;
  `MarketZone` — аналогично (`Trade/Scripts/Network/MarketZone.cs:256,304`).
- Замеры: «Ферма Примума 0_1» — 82.93 ms self / 136.6 KB GC за один полл против
  0.1–0.3 ms / <1 KB у остальных зон. Цена сидит в C#-цикле по хитам
  (`GetComponentInParent<NetworkPlayer/ShipController>` на каждый), а не в самом запросе
  (OverlapSphere там же — единицы мс). Плюс каждый `OverlapSphere` аллоцирует managed-массив.

## Почему это тормозит (механика)

1. PhysX broadphase (AABB-дерево) 9 712 боксов жуёт легко — симуляция всей физики
   стоит ~3 ms/кадр (см. `00_CAPTURE_*`, §5).
2. Но `OverlapSphere r=1000` возвращает **все** пересекающиеся AABB — на ферме это сотни
   коллайдеров за вызов. Дальше C#: массив + `GetComponentInParent` (проход вверх
   по иерархии) на каждый хит. 10 зон × 2 опроса × 4 Гц = до ~80 таких проходов в секунду,
   синхронно — пилы 50–100 ms.
3. Маска `~0` означает: зоны перебирают вообще всё, включая заведомо мусорные слои.

Вывод: узкое место — не PhysX и не число боксов само по себе, а связка
«километровый радиус + все слои + per-hit C#». Поэтому Фаза 1 (десинхрон/буферы) дала
только −27% GC и не убрала пилы.

## Варианты (что делать)

### Вариант A — сузить `pollLayerMask` (рекомендуется первым)
Поле уже есть (`OuterCommZone.cs:36-39`, тултип советует). Игроков и корабли положить
на выделенные слои (если ещё не), маску зон сузить до них. Меняется только данные сцен
(инспектор), код не трогается. Ожидание: число хитов на ферме падает на порядки,
пилы уходят. Проверка: захват до/после + ручной тест детекта (T-key, CommPanel, маркет).
Риск: низкий, но пропущенный слой = «зона не видит» — проверять руками.

### Вариант B — меньше коллайдеров на ферме
В проекте уже есть `Assets/_Project/Editor/CombineMeshesToCollider.cs`: сливает меши
детей в один комбинированный MeshCollider (convex=false) на корне. Но осторожно:
- Один большой concave-меш против `OverlapSphere` — это sphere-vs-triangles, поштучно
  дороже, чем sphere-vs-box. Выигрыш — за счёт количества объектов, проигрыш — за счёт
  цены одного теста. Для статичной фермы обычно всё равно выигрыш, но **мерить**.
- Дешевле всего для опросов — несколько крупных боксов вместо сотен мелких
  (примитив против примитива — самый быстрый narrowphase).
- Прежде чем объединять: убедиться, что геймплей не зависит от поштучных коллайдеров
  фермы (сбор, урон по объектам, raycast-выбор). Если зависит — только вариант A.

### Вариант C — код опросов (Фаза 2 плана)
`OverlapSphereNonAlloc` с per-instance буфером + счётчик переполнений (не молчаливая
обрезка), кэш `GetComponentInParent` по `NetworkObjectId`. Снимает GC массива и часть
C#-цены, но не число хитов. Делать вместе с A, не вместо.

### Не делать
- Не ставить `convex=true` на меш-ферму ради Rigidbody — для статики только дороже и сломает
  CharacterController-путь (см. комментарий в `CombineMeshesToCollider.cs:172`).
- Не удалять коллайдеры фермы целиком без проверки геймплея (см. выше).

## Как принять решение (протокол)

1. В сцене посмотреть слои объектов фермы (если все на Default — сначала разложить по слоям).
2. Применить вариант A на одной зоне (Ферма 0_1), снять захват 60 с: сравнить self/GC полла.
3. Если пила осталась — вариант B на тестовой копии фермы + замер.
4. Цифры — в `ITERATIONS.md`, решение фиксируем здесь.
