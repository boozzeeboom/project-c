# 01 — Ядро теории подключаемых мозгов

> Вопрос пользователя своими словами: «клиент видит многих — сервер не обрабатывает ничего; когда клиент бьёт, сервер включает этого одного из многих, отправляя ему "мозги", и ещё 2–3–7 соседним на стычку; а толпа остальная остаётся у клиента. То же про разговор: у клиента 100500 человек, у сервера только герои, но как только игрок говорит с кем-то — он становится героем на день / получает из пула диалоги, квесты».

Эта теория формализует сказанное в рабочую схему. Название рабочее: **Roster + Lease (ростер + аренды)**.

## 1.1 Три инварианта (нарушать нельзя)

**I1. Существование ≠ мышление.** Каждый видимый человек существует на сервере как строчка ростера (байты), но думает только тот, у кого арендован слот. Нет аренды — нет тика. Точка.

**I2. Событие игрока — единственный повод думать.** Толпа не тикает «авось пригодится». Мозг выдаётся только по событию: удар, разговор, скрипт (тревога, квест-триггер). Событие кончилось + TTL истёк → мозг отобран.

**I3. Бюджет важнее справедливости.** Одновременных думающих — не больше капа зоны/игрока. Кто не влез — получает дешёвый фолбэк (убежать, съёжиться, встать в очередь на разговор). Лагать ради «честности для 150-го» запрещено.

Из этих трёх следует вся остальная конструкция. Кто предлагает «давайте толпа будет чуть-чуть тикать» — нарушает I1 и возвращается к смерти сервера. Кто предлагает «давайте в драке думать будут все» — нарушает I3.

## 1.2 Сущности (минимальный набор)

```
CROWD (клиент)              SERVER
─────────────               ────────────────────────────
визуал (тело,               РОСТЕР: crowdId → {приписка,
 анимация, якорь)             жив, HP, отношение, обида,
                              дом-якорь, внешность-сид}
      │                       ▲ │ ▲
      │-invalidate/seed        │ │ │-дельты (только наблюдателям)
      ▼                       │ │ ▼
CROWD MANAGER ◄── lease ──► ПУЛЫ: BrainPool (бой),
 (пул 40–60 видимых,           DialogPool (разговоры),
  LOD, петли)                  HeroRegistry (кто сейчас герой)
```

- **crowdId** — стабильный строковый ID человека толпы (`ship_gigant:deckB:042`, `primum:alley:3117`). Живёт дольше сессий, переживает перезаходы (как `memberId` в `ShipCrewManifest`, только для тысяч). По нему сервер хранит отношение/обиду/квест-флаги.
- **Ростера достаточно для 100% «пассивных» взаимодействий**: пинок (урон по записи), осмотр (имя/фракция/гreeting), отношение (`ModifyNpcAttitude`-эквивалент), смерть/воскрешение по расписанию.
- **Герой = crowdId + активная лиза.** Лиза — это `{slotId, crowdId, reason: Combat|Dialog|Script, ownerClientId, expiresAt, renewOn: [damageEvent, dialogOpen, ...]}`. Пока лиза жива — человеку положен тик/сессия/репликация. Умерла — остался только итог в ростере.
- **Пулы конечны и раздельны.** Бой и разговор — разные пулы (разные цены). Боевой слот — это право на серверный combat-tick + урон в ответ. Диалоговый слот — право на `QuestWorld`-сессию + дерево + квест-экшены. Нельзя съесть диалоговый слот дракой.

## 1.3 Жизненный цикл человека толпы (единый для боя и разговора)

```
BORN (ростер: приписан к якорю, HP full)
  │  клиент в AOI → визуализирован из пула (тело по сиду внешности)
  │
  ├─► IDLE (сервер: ничего не делает; клиент: петля/якорь)
  │
  ├─► событие E1 (удар) ──► PROMOTE Combat? ──► HERO_COMBAT ──► DEMOTE ──► IDLE
  │                           (пул/бюджет/валидация)   (лиза TTL,       (итог в ростер:
  │                                                     продление        HP, обида, смерть?)
  │                                                     уроном)
  ├─► событие E2 (разговор) ─► PROMOTE Dialog? ──► HERO_DIALOG ──► DEMOTE ──► IDLE
  │                             (пул/бюджет/дистанция)   (лиза TTL,       (итог: отношение,
  │                                                       продление        квест-флаг,
  │                                                       репликами)       «герой на день»?)
  └─► событие E3 (скрипт: тревога/квест) ─► PROMOTE Script ─► ... ─► DEMOTE
```

Промоут — это всегда 4 шага (одинаковые для боя и диалога, детали в `02`/`03`):

1. **Validate** — сервер проверяет событие (дистанция, LOS, кулдаун, рейт-лимит). Клиентскому слову не верит.
2. **Admit** — проверка бюджета и пула. Нет места → фолбэк (не лаг).
3. **Bind** — `crowdId ↔ slotId`, сервер рассылает наблюдателям дельту `HERO_UP {crowdId, apparenceSeed, anchorHint, reason, ttl}`.
4. **Renew/Expire** — слот продлевается только живыми событиями (урон/реплики). Тишина → демotion и `HERO_DOWN {crowdId, outcome}`.

## 1.4 Почему это рабочая схема, а не фантазия (математика)

Три стены, в которые упирается «150 честных NPC» (подробно — в корневом анализе наполнения):

1. **Сеть.** `NetworkTransform` на 150 тел × ~10 Гц × ~50 байт ≈ 75 КБ/с на каждого наблюдателя + спавн-шторм при входе в зону. В схеме Roster+Lease сеть несёт: ростер — 0 (не реплицируется), толпа — 0 (клиентская), герои — `HERO_UP/DOWN` (единицы пакетов) + тик только героев (6–10 тел). Порядок экономии — ×15–25.
2. **Сервер CPU.** Полный `NpcBrain` — это `Update` + `FixedUpdate` (SphereCast-платформа) + `SocialBrain.Tick` + NavMesh-avoidance O(n²) в тесноте. В схеме тикают только герои (≤ капа). Толпа стоит в ростере — 0 тиков. Урон по толпе — это запись в словарь + `NetworkVariable`-подобная дельта HP по требованию, а не тик.
3. **Клиент GPU/CPU.** 150 уникальных скинов — 150 draw calls + skinning + тени. В схеме клиент тоже пулит: видимых тел 40–60 из 3–5 shared-мешей, остальные «за стеной» не инстанцированы (см. `05`). Это уже клиентская половина теории, без неё серверная не спасёт.

Ключевое свойство, делающее схему реализуемой именно у нас (а не «в теории»):

- **Бой:** `IDamageTarget` (`Scripts/Combat/Core/IDamageTarget.cs`) — чистый интерфейс без наследования от `MonoBehaviour`. Серверная запись толпы может его реализовать как данные. `CombatServer._targets` — словарь `ulong → IDamageTarget`; ему всё равно, GameObject это или строчка ростера. Значит, «ударить толпу» не требует `NetworkObject` на толпе. Требует только синтетический `targetId` и позицию для range/LOS-проверок (уже есть в `CombatServer.cs:206–242`).
- **Разговор:** `NpcController` (`Quests/NpcController.cs`) — обычный `MonoBehaviour`, не `NetworkObject`. `QuestServer.RequestTalkToNpcRpc` (`Quests/Network/QuestServer.cs:491`) уже работает как «промоут по требованию»: дистанция через `NpcController.Find(npcId) + IsWithinDistance`, личность через `questDatabase.GetNpc(npcId)`, дерево через `defaultDialogTree` или runtime-fallback (`GetOrBuildFallbackTree`). Значит, «поговорить с толпой» не требует сетевого тела. Требует только резолвер `npcId → позиция/дефиниция` для толпы и пул сессий (уже есть — `QuestWorld` сессии на `clientId`).

То есть обе половины теории ложатся на существующие швы, а не требуют переписать бой и квесты.

## 1.5 Что значит «герой на день» в терминах лиз

Фраза пользователя «становится героем на день» — это лиза с длинным TTL и персистентным итогом:

- **Короткая лиза (бой):** TTL 20–30 с, продление каждым уроном/событием тревоги. Кончилась → демotion, в ростере остались HP/обида/смерть.
- **Средняя лиза (разговор):** TTL сессии + grace-период (например, 5–10 минут после закрытия диалога человек ещё «тёплый»: его легко найти, он помнит тему). Кончилась → демotion, в ростере остались отношение/квест-флаг.
- **Длинная лиза («герой на день»):** пометка в ростере `heroUntil = now + 24ч (игровых)`. Человек визуально и серверно приоритетен: его визуал не вытесняется из клиентского пула, его `npcId` резолвится быстрее, ему положено именное дерево/квест, его обида не протухает по `grudgeDurationSec=300с`, а живёт до конца лизы. Тика всё равно нет, пока нет активного события, — это важно: «герой на день» ≠ «думает весь день». Это «повышен в правах», а не «посажен на тик».

|---|---|---|---|---|
| crowdId, дом-якорь, сид внешности | ✅ всегда | — | кэш по сиду | только `HERO_UP` наблюдателям |

| Отношение/обида/фракция | ✅ (`QuestWorld`-подобные таблицы) | читает/пишет | читает для бейджа | по событию |

| Квест-флаги | ✅ | пишет | — | снапшот по запросу |

## 1.7 Связь с тирами из корневого анализа

- Tier-0 «герои по должности» (капитан, торговцы) — это перманентные лизы, вне пула. Их 5–12, они не конкурируют с толпой.
- Tier-1 «функциональные» (механики у постов) — это ростер + длинные лизы без тика + короткие лизы при событии. Их 20–40.
- Tier-2 «толпа» — чистый ростер + клиент. Их сотни/тысячи. Героями становятся только через промоут.

Формула ощущения: `видимых_тел (40–60) + именных_героев (5–12) + память_о_вчерашних (герои-на-день) ≫ серверных_тиков (≤10)`.
