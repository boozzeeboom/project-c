## Главное отличие от Cobble и остальных: кладка — **регулярная сетка**, а не Worley

У мостовой (`Cobble/`) рисунок начинается с ячеек Worley: камни разного размера,
шов = `F2 − F1`. Для кирпича это неверно: у кирпича **постоянный размер и перевязка
рядов**, а «живость» даёт не разброс формы, а то, что кладку ведёт рука каменщика
(искривление сетки) и то, что кирпичи разного тона.

Поэтому сетка кладки — арифметическая (`floor`/`frac` по масштабированным
координатам), а Worley в этом материале отвечает **только за поры** и больше нигде
не появляется.

```
p  = ObjectPos * BrickScale + BrickSeed
q  = float2(p.x, p.y * BrickAspect)          // Aspect = длина / высота кирпича
q += (noise2(p*0.6) − 0.5) * JointWarp       // кладку «ведёт» (JointWarp)
row = floor(q.y)
q.x += row * RowOffset                       // перевязка (0.5 = в полкирпича)
f  = frac(q);  d = min(f, 1 − f)
edge = min(d.x / JointWidthX, d.y / JointWidthY)
Joints = 1 − smoothstep(0, 1, edge)
```

Два следствия, заложенные в конструкцию:

1. **Тон кирпича считается той же сеткой** (`floor(q)` → хеш ячейки). Он физически
   не может разъехаться со швами — в отличие от «двух независимых шумов», где тон
   начинает ползти относительно границы кирпича.
2. **Швы разной ширины** (`_Joint_Width_X` 0.055 против `_Joint_Width_Y` 0.13) —
   не украшательство: у реальной кладки шов 1 см при кирпиче 21.5 × 6.5 см даёт
   0.046 доли длины, но 0.154 доли высоты. Одна общая ширина сделала бы либо
   вертикальный шов вдвое толще горизонтального, либо наоборот.

### Пояснение по слоям

- **Швы раствора.** Полоса у границы ячейки; `edge` — «во сколько раз ширина шва
  больше расстояния до границы», поэтому `1 − smoothstep(0, 1, edge)` даёт 1 ровно
  на шве и 0 в середине кирпича. Разные ширины по X и Y — см. выше.
- **Тон кирпича.** Постоянная внутри кирпича величина со скачком на границе: в стене
  всегда есть пережжённые и недожжённые кирпичи, и именно это, а не поры, читается
  как «набрано из разного кирпича». `_Brick_Tone` управляет размахом подмешивания
  светлого тона.
- **Зерно.** Один примитив (fbm, 3 октавы) в двух ролях: песок на лице кирпича
  (`_Face_Grain_Stretch` = 3 вытягивает зерно вдоль локальной X — «сдирное» лицо
  формы) и крупа раствора (Stretch = 1, изотропно). У раствора второй аргумент
  слота — **константа 1**, а не свойство.
- **Поры.** `F1`-расстояние до центра ячейки Worley: 0 в центре поры. Радиус у каждой
  ячейки свой (`w × lerp(0.35, 1.0, hash)`), и примерно треть ячеек поры не имеет
  вовсе (`smoothstep(0.22, 0.42, hash)`) — иначе поверхность читается ситом,
  а у кирпича поры редкие и разного размера.
- **Трещинки.** `Groove = abs(fbm × 2 − 1)` — расстояние до «линии» fbm, поэтому
  ширина задаётся отдельным `_Crack_Width`, а не выводится из самой линии. Сетка
  растянута по локальной Y (`_Crack_Stretch` = 4), это и разворачивает трещины
  **вверх по стене** (так раскалывается кладка при осадке). Крупный fbm решает,
  где трещина раскрылась, но не обрывает её насовсем: глубина модулируется
  `lerp(0.35, 1.0, opened)`.
- **Высолы.** Изотропное fbm-пятно (Stretch = 1 — константа слота), порог —
  `Smoothstep(_Efflo_Threshold, _Efflo_Threshold + _Efflo_Softness, пятно)`.
  Ключевая деталь: маска **прижата к швам** — в цепочку домешивается
  `Saturate(швы×_Joint_Amount + 0.45)` (Add `5b8b087c`, константа 0.45 — **значение
  слота, не свойство**). Высолы идут по швам и по раствору, а не пятнами по полю.
- **Грязь.** Тот же примитив, но `_Dirt_Stretch` = 4 — пятно вытянуто вдоль
  **локальной Y** (грязь стекает вниз по стене), и порог свой.

## Ядро шума — `Assets/_Project/Shaders/ProceduralBrickNoise.hlsl`

Правило **T-BRONZE01** соблюдено: все экспонированные функции — **одно-выходные**
(File-режим), их сигнатуры совпадают с порядком слотов CF-нод в графе. Новое
поведение — **новой** функцией; существующие сигнатуры не менять (слоты связываются
по номеру).

| Функция (имя CF-ноды) | Входы | Выход | Что считает |
|---|---|---|---|
| `ProceduralBrickJoints` | `ObjectPos, BrickScale, BrickAspect, RowOffset, JointWarp, JointWidthX, JointWidthY, BrickSeed` | `Joints` | сетка кладки + `d = min(f, 1−f)` + `edge = min(d.x/JointWidthX, d.y/JointWidthY)` → `1 − smoothstep(0,1,edge)` |
| `ProceduralBrickTone` | `ObjectPos, BrickScale, BrickAspect, RowOffset, JointWarp, BrickSeed` | `BrickTone` | `hash13(float3(floor(q), BrickSeed + 11))` — та же сетка, что у швов |
| `ProceduralBrickGrains` | `ObjectPos, GrainScale, GrainStretch, GrainSeed` | `Grains` | `fbm↓3(p, 2.0)`, `p.x /= GrainStretch` — вытянуто вдоль локальной X |
| `ProceduralBrickPores` | `ObjectPos, PoreScale, PoreWidth, PoreSeed` | `Pores` | Worley F1 (3×3×3), `radius = w × lerp(0.35, 1.0, hash ячейки)`, треть ячеек пустые |
| `ProceduralBrickCracks` | `ObjectPos, CrackScale, CrackStretch, CrackWidth, CrackWarp, CrackSeed` | `Cracks` | `p.y /= CrackStretch` → домен-warp → `Groove(fbm)` → `× lerp(0.35, 1.0, opened)` |
| `ProceduralBrickPatch` | `ObjectPos, PatchScale, PatchStretch, PatchSeed` | `Patch` | `fbm↓3(p, 2.0)` без порогов, `p.y /= PatchStretch`; порог ставится в графе |

Внутренние хелперы (на них граф не ссылается): `PCBrick_Hash13` (хеш без `sin`),
`PCBrick_ValueNoise3`, `PCBrick_Fbm3` (3 октавы, нормировка `/0.875`),
`PCBrick_Groove` (`abs(s×2 − 1)` — именно расстояние, а не `1 − |2s−1|`),
`PCBrick_Grid` (общая сетка швов и тона). У каждой `_float`-функции есть
`_half`-вариант через `float`-перегрузку.

CF-нод **8**, все ссылаются на HLSL по GUID `062473832f74f9242aaaf758a1b4146d`:
`ProceduralBrickJoints`, `ProceduralBrickTone`, `ProceduralBrickGrains` ×2,
`ProceduralBrickPores`, `ProceduralBrickCracks`, `ProceduralBrickPatch` ×2.

## Цепочки (все проверены по рёбрам графа)

### Альбедо — 8 последовательных `Lerp`

| # | Нода | A | B | T (порог) |
|---|---|---|---|---|
| 1 | `98d231d3` | `_Brick_Color` | `_Brick_Light_Color` | тон × `_Brick_Tone` |
| 2 | `ab3d7d2d` | ←1 | `_Brick_Light_Color` | зерно кирпича × `_Face_Grain_Amount` |
| 3 | `482b9725` | ←2 | `_Mortar_Color` | швы × `_Joint_Amount` |
| 4 | `e4841169` | ←3 | `_Efflorescence_Color` | (крупа раствора × `_Mortar_Grain_Amount`) × (швы × `_Joint_Amount`) |
| 5 | `0b66f7b6` | ←4 | `_Dirt_Color` | поры × `_Pore_Amount` |
| 6 | `6a1f7dff` | ←5 | `_Dirt_Color` | трещины × `_Crack_Amount` |
| 7 | `ae954db9` | ←6 | `_Efflorescence_Color` | `Smoothstep(высолы) × Saturate(швы×_Joint_Amount + 0.45)` × `_Efflo_Amount` |
| 8 | `379ef6d2` | ←7 | `_Dirt_Color` | `Smoothstep(грязь) × _Dirt_Amount` |

Выход 8-й (`379ef6d2`) → блок `SurfaceDescription.BaseColor` (`dc3eeeb4`);
в сгенерированном шейдере это `surface.BaseColor = _Lerp_379ef6d2…_Out_3_Vector4.xyz;`.

**Зерно кирпича применяется ДО шва (шаг 2 раньше шага 3)** — шов затирает зерно
собой, поэтому `OneMinus` не нужен и песок не «просвечивает» сквозь раствор.
Обе группы высолов/грязи идут **после** шва: они живут поверх кладки, а не под ней.

Порог 4-й ступени — не «просто пятно»: он перемножает крупность раствора и шов,
то есть высолы садятся именно на шов и раствор. Шестая ступень (грязь в трещинах)
идёт **до** седьмой (высолы) — так высолы перекрывают грязь в трещинах, а не наоборот.

### Глянец

```
Smoothness = Saturate( _Smoothness + тон × _Brick_Gloss + (швы × _Joint_Amount) × _Mortar_Gloss )
```
Ноды: Add `f0320f0a` (база + тон), Multiply `0eeb0375` (тон × `_Brick_Gloss`),
Multiply `8bf9cb8a` (швы × `_Joint_Amount`), Multiply `4a090c70` (… × `_Mortar_Gloss`),
Add `120fa509`, Saturate `ce40446f` → блок `beadeeeb` (Smoothness).
`_Mortar_Gloss` — **отрицательный**: раствор матирует, в отличие от кирпича.

### Порядок входов `Smoothstep` — естественный

ShaderGraph собирает `SmoothstepNode` как `Out = smoothstep(Edge1, Edge2, In)`
(слот 0 = Edge1 — нижний порог, 1 = Edge2 — верхний, 2 = In — значение).
У бронзы (и унаследованно у Wood/IronRust) провода перепутаны, поэтому там порог
выходит обращённым. **В Brick значение всегда подаётся в `In` (слот 2), пороги —
в `Edge1`/`Edge2`**: проверено на графе, `Smoothstep = 2` из 2, и оба порога собраны
как `Add(Threshold, Softness)` (ноды `b3745575` для высолов, `c105228a` для грязи).
Подробный разбор исходной путаницы — в `Concrete/README.md`.

## Рельеф: почему здесь он работает

Вход высоты — **четырёхчленная сумма, у каждого вида свой коэффициент, общего
множителя нет**:

```
hSum = Add( Add( швы × _Joint_Bump , поры × _Pore_Bump ) ,
            Add( трещины × _Crack_Bump , тон × _Brick_Lift ) )
```

Ноды: множители `5102c1e8` (швы × `_Joint_Bump`), `ba55e0cd` (поры × `_Pore_Bump`),
`cc80ce7c` (трещины × `_Crack_Bump`), `267dc525` (тон × `_Brick_Lift`);
Add `79ba556d`, Add `f413245f`, итоговый Add `137930f4` → `Normal From Height.In`.

**Ровно это и было дефектом в Cobble/Bark/Concrete/Plastic**, поэтому проверка
обязательная. Все три пункта из `docs/Materials/README.md`, замеры — по графу и по
сгенерированному шейдеру:

| # | Проверка | Результат |
|---|---|---|
| 1 | нативные `m_Id` слотов `NormalFromHeightNode` | `In = 0`, `Strength = 2`, `Out = 1`: ребро высоты приходит на `m_SlotId 0` (`137930f4[2] → df2b8057[0]`), `_Bump_Strength` — на `m_SlotId 2` (`9c4dde78[0] → df2b8057[2]`), выход уходит на `m_SlotId 1` (`df2b8057[1] → 9f06e243[0]`, блок `SurfaceDescription.NormalTS`) |

| 3 | `surface.NormalTS` в том же тексте | `surface.NormalTS = _NormalFromHeight_df2b8057…_Out_1_Vector3;` |

`_Bump_Strength` (нода свойства `9c4dde7881dc47a48e03cdd2f9f52146` = `_Bump_Strength = 1`)
встречается в сгенерированном шейдере 14 раз, включая присваивание
`float _BumpStrength_9c4dde78…_Out_0_Float = _Bump_Strength;`.

Значит силу рельефа можно править **из пресета**, не трогая граф, а `_*_Bump`
остаются амплитудами высоты со своим знаком (швы и поры вниз `−0.9` / `−0.35`,
трещины вниз `−0.5`, подъём кирпича вверх `+0.15`).

> Cobble, Bark, Concrete (шаблонный `float(0.01)` → рельеф погашен ×100) и Plastic
> (цепочка рельефа не вызывается вовсе) **не правились**: это меняет утверждённый
> вид материалов. Brick — эталон того, как это должно выглядеть.

## Требования к геометрии

1. **Локальная Y — вверх по стене, X — вдоль ряда.** Сетка кладки считается из
   `(p.x, p.y)`, ось Z в неё не входит: стена обязана лежать в локальной плоскости
   XY. Если меш развёрнут «лёжа», кирпичи пойдут вдоль мировой горизонтали
   неправильной стороной.
2. **UV не нужны вообще** — ни один слой не читает UV.
3. **Единичный габарит не требуется**: маски кромок в материале нет (кромка стены —
   это край меша, а не признак материала), поэтому ни `_Edge_Position`, ни
   нормировки размеров не нужно.
4. **Фаски не нужны.** Рисунок целиком процедурный, геометрия на него не влияет.
5. **Локальный масштаб влияет на частоту.** Всё считается в object-space, поэтому
   масштабирование объекта в сцене масштабирует и рисунок. Для мелкой детали
   поднимать `_Brick_Scale` (и, если нужно, `_Pore_Scale`), а не масштабировать объект.
6. **Кривизна меша искажает кладку.** Рисунок идёт по локальным координатам, а не по
   поверхности: на сильно выгнутой стене кирпичи «проецируются» и шов местами
   стягивается. Для арочных и поворотных участков нужен отдельный пресет с меньшим
   `_Brick_Scale` либо ручная геометрия.

## FO-safe (Floating Origin)

- Весь шум — от `Position (Object)`: нода `2b833304`, `m_Space = 0`; вход `ObjectPos`
  у всех 8 CF-нод приходит от неё же.
- `AbsoluteWorld` в графе — **0 вхождений**.
- Вариативность между объектами — сид-свойствами (`_Brick_Seed`, `_Face_Grain_Seed`,
  `_Mortar_Grain_Seed`, `_Pore_Seed`, `_Crack_Seed`, `_Efflo_Seed`, `_Dirt_Seed`),

## Грабли формата `.shadergraph` (для будущих правок)

1. Файл — поток JSON-документов, разделитель — `}` + пустая строка + `{`.
   **Пустая строка внутри документа обрывает документ.** Проверено на этом графе:
   `docsWithBlankLineInside = 0`.
   Ноды и слоты лежат **отдельными** документами, а списки (`m_Nodes`) и **все рёбра**
   (`m_Edges`) — внутри одного документа `GraphData`. Поэтому разбор «по документу»
   найдёт только одно ребро из 122; рёбра надо искать по всему тексту сразу.
2. Переводы строк по проекту разные. `Brick.shadergraph` — **чистый LF**
   (`CR = 0`, `LF = 13935`): сборщик и проверки режут по литералу `}\n\n{`.
   У `Concrete.shadergraph` после точечной правки стал CRLF — инструмент, режущий по
   литералу, увидит **один** документ вместо сотен. Перед текстовым разбором
   нормализовать переводы строк или резать по `}\s*\n\s*{`. Для импорта Unity это
   безразлично.
3. Слоты нумеруются значением `m_Id`, и оно **не всегда равно позиции в массиве**:
   у `CustomFunctionNode` порядок естественный (`ObjectPos = 0`, входы `1…N`,
   выход `N+1`), а у `NormalFromHeightNode` — `In = 0`, `Strength = 2`, `Out = 1`.
   Перенумерация по индексу молча убивает цепочку рельефа (см.
   `docs/Materials/README.md`).
4. Значение по умолчанию входа правится в `m_Value` слота; у `Vector1MaterialSlot`
   дублируется в `m_DefaultValue`, у динамических слотов (Add/Multiply/Lerp/
   Smoothstep) значение имеет вид `{x,y,z,w}`.
5. Свойства блэкборда адресуются по `m_ObjectId`; `PropertyNode` ссылается на
   свойство через `m_Property.m_Id`. **Ребра ссылаются на `m_ObjectId` ноды**,
   а не на `m_ObjectId` свойства — проверка «источник — `PropertyNode`» обязана
   смотреть тип ноды-источника.
6. Целевой рендер — URP Lit (`UniversalTarget` + `UniversalLitSubTarget`), Forward.
