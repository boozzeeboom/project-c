# 17 — T-MB06: официальный MotionBricks runtime на owner-персонаже

> **Дата:** 2026-11-16
> **Статус:** runtime-код, standalone TensorRT и UDP smoke проверены; **визуальная приёмка на живом персонаже ещё не проведена**. 17.11 внесён fix пространства эталонного root (см. §4.5) — требуется повторная визуальная приёмка.
> **Цель:** проверить непрерывную генерацию как в preview NVIDIA, а не новые offline-переходы. Движение, бой, сеть и префабы игрока не меняются.
> **Design:** [T-MB06_RUNTIME_SIDECAR.md](../../dev/T-MB06_RUNTIME_SIDECAR.md)

## 1. Что реализовано

```text
NetworkPlayer + CharacterController
    ↓ фактические position / rotation / velocity / dt
Python sidecar: SOMACharacter + StateMachine + Smart Primitives
    ↓ GeneratedMotionPlayer + TensorRT + MotionRecorder
77 SOMA joint transforms + 4 foot contacts
    ↓ UDP loopback, latest complete frame
SOMA → Project C rig в LateUpdate
```

Это не воспроизведение заранее запечённого `.anim`: sidecar использует официальные
`SOMACharacter`, `StateMachine`, `GeneratedMotionPlayer`, `MotionRecorder`, Smart Primitive
clips и `MotionBricksSOMAEngine`. При locomotion возникают новые TensorRT-генерации;
`playback_source` различает `generated`, `clip_transition` и `clip`.

`CharacterController` остаётся единственным источником перемещения. Runtime не вызывает
`Move`, не меняет `NetworkPlayer`, не реплицирует кости и не определяет hitbox/урон.
Root генерации связывается с фактическим положением и yaw игрока; вертикальный bob
генерации сохраняется. История recorder получает уже скорректированную показанную позу.

Файлы:

- `tools/runtime_sidecar.py` — официальный runtime, внешний root, UDP, self-test и метрики.
- `tools/verify_root_frame.py` — численная проверка контракта корня: считает `delta_root`
  так же, как C#, и печатает угол/ось (порог 30°; регрессия даёт ~90°).
- `MotionBricksRuntimeClient.cs` — запуск процесса, async logs, background receive,
  latest-frame, RTT/inference/process diagnostics и shutdown.
- `MotionBricksSomaRetarget.cs` — SOMA bind/rest → 22 кости Project C, world-delta rotations,
  ограничения ключиц и twist рук ±90°, вертикальная поправка таза; `B-jaw` необязателен.
  `SourceToTargetYawOffsetDeg = 0`: ретаргет переносит только `frame·bind⁻¹`, и mirror
  `ToUnityRot = (x, −y, −z, w)` в этой дельте сокращается, поэтому отдельный yaw не нужен
  (прежние `+90°` были измерены на абсолютной ориентации пакета и не лечили завал — §4.5).
- `MotionBricksRuntimePlayback.cs` — owner-only playback, A/B, fallback, body-swap guard
  и временный authored Animator на прыжке с автовозвратом после приземления.
- `MotionBricksRuntimeReviewMenu.cs` — ручной Attach/Start/Stop/Detach/Diagnostics.

Attach выбирает rest template из фактических serialized-моделей `CharacterCustomisationApplier`
(`_maleModel`/`_femaleModel` по `CurrentBodyType`); HumanM/HumanF остаются fallback для KL-аватаров.
Это поддерживает текущий male `testing.fbx` с аватаром `testingAvatar` и female-после body swap.

## 2. Изоляция и переключение

Runtime находится под `#if UNITY_EDITOR`, добавляется только вручную в Play Mode и не
сохраняется в prefab/сцену. Python, TensorRT, ONNX и sample motions не копируются в `Assets`
и не попадают в build. Обычный Animator Controller не заменяется.

- **Attach + start** запускает neural preview на локальном owner.
- **Ctrl+F10** переключает neural preview и authored Animator.
- **Stop / restore Animator** оставляет sidecar живым для повторного A/B.
- **Detach** останавливает sidecar и удаляет runtime-компонент.
- Потеря owner, отключённый CharacterController, каст, stale pose, ошибка протокола или
  завершение sidecar возвращают authored Animator.
- Body swap останавливает neural preview и обновляет ссылку Animator; автоматический
  повторный запуск после свапа не выполняется.

Старый baked playback/root motion на том же игроке отключается при запуске neural preview.
Это защита эксперимента, а не production-rollout.

## 3. Протокол

UDP IPv4 loopback, little-endian, magic `MBR1`, version 1. Порт по умолчанию — **39360**, и он
намеренно ниже динамического диапазона Windows (49152–65535): исключённые UDP-диапазоны
(Hyper-V/WSL/Docker) вырезаются именно из него и переезжают при перезагрузке. Один запуск дал
`PermissionError: [WinError 10013]` на `sock.bind((host, port))` — 49360 оказался внутри
49287–49386 → Unity получила `FALLBACK: sidecar exited`. Если sidecar снова не поднимается,
первым делом: `netsh int ipv4 show excludedportrange protocol=udp` — порт не должен попадать ни в
один из диапазонов.

| Пакет | Размер | Содержимое |
|---|---:|---|
| Unity → sidecar request | 64 байта | sequence, flags, dt, walk/run speeds, position, rotation, velocity |
| Bind response | 2204 байта | header 48 + 77×7 float |
| Pose response | 2220 байт | header 48 + 77×7 float + 4 contacts |
| Error response | header + UTF-8 | диагностика исключения sidecar |

Bind-поза передаётся отдельным packet из официального skeleton; файл `soma_bind.f32` для
этого runtime не нужен. Флаги request: `reset=1`, `shutdown=2`.

Unity не ждёт inference: receive работает в background thread, визуальный слой берёт
последний целый кадр. При stale timeout происходит fallback. Метрики включают engine init,
wall inference p50/p95/max, официальные CUDA stages, IPC RTT/age, sent/received FPS,
generation count, RAM процесса, fallback count и причину остановки.

### 4.5. Пространство эталонного root (fix 17.11)

Симптом приёмки 16.11: персонаж бежит «шиворот-навыворот», его крутит, геометрия ломается.
Причина — постоянная ошибка ориентации в **joint 0**. Из 77 джойнтов только у корня пространство
имеет значение: у остальных дельта `frame_local·bind_local⁻¹` конвенция-инвариантна. А
официальный проигрыватель пишет joint 0 в **двух разных конвенциях**:
`clip.animation.sample()` оставляет model space (эти же позы идут в inference как target poses),
а декодер пишет уже runtime space (`output_local_poses[frame, 0] = mul(model_to_runtime, hips)`).
`model_pose()` при этом всегда снимает `runtime_to_model`, поэтому любой *сэмплированный* эталон
давал постоянную ошибку, независимую от движения: `_apply_external_root` ставит
`pose[0].rot = yaw_delta · эталон`, и в C# уходит `delta_root = эталон_в_Unity · bind⁻¹`.

| Эталон root'а | `delta_root` | Что видно |
|---|---:|---|
| bind-клон до `_sample_playback` (состояние 16.11) | 90.0° вокруг X | завал корпуса на бок |
| первый клип-кадр после `_sample_playback` (промежуточный) | 93.6° вокруг Y | корпус боком к движению |
| `model_to_runtime · bind_root` (текущий) | 0.0° | корпус следует за игроком |

Цифры получены `tools/verify_root_frame.py` на реальном sidecar (idle, 5 м/с, поворот 90°):
скрипт повторяет формулу C# — `ToUnityRot(packet_root) · ToUnityRot(bind_root)⁻¹` — а не
абсолютную ориентацию пакета. Отсюда важный вывод: замер «root-forward пакета `−X` против
rest-forward `+Z`» (из которого раньше вывели `+90°` yaw) относится к **абсолютной** ориентации
после зеркала осей и в дельте не участвует.

Исправление: эталон корня теперь `model_to_runtime · bind_root`
(`_bind_reference_root_rotation`). Тогда пакетный root совпадает с bind **точно**, `delta_root`
равен identity на idle, на 5 м/с и после поворота на 90° (0.0° во всех точках), а ориентацию
тела задаёт трансформ игрока — double-count невозможен, потому что `model_pose()` вычитает
текущий app-rotation из root'а. Вертикальный контракт §4.2 не изменился: оба поля эталона
читаются из `pose[0,2]` и сокращаются.

**Инвариант:** эталонный root — это bind, переведённый в runtime space; не bind-клон
(model space) и не сэмплированная поза (её пространство зависит от `playback_source`).

### 4.6. Скрутка позы при круговом вводе (fix 17.11, второй)

Симптом приёмки 17.11: руки «напутаны», ноги ведут не туда, а при цикле
`W→D→S→A→W…` персонаж, «как dummy на нитке», закручивается и после отпускания кнопок
раскручивается обратно.

Проверено, что это **не** ретаргет: у `HumanM_Model.fbx` (rest) и SOMA bind совпадают
направления сегментов (плечи ±X, бёдра −Y, носок стопы +Z в обоих), поэтому перенос
мировой дельты `delta · RestWorld` даёт ту же деформацию, что у источника (углы костных
*фреймов* разные — bind `B-upperArm.L` = 90° вокруг X против 93.8° вокруг Z у rest, —
но деформация от этого не зависит).

Причина — **порядок в `step_character`**: `_apply_external_root` писал выровненный под
игрока корень в `current_pose` ДО `record_pose`, т.е. в историю модели уходил не её
собственный корень. Официальный `Character.step()` пишет sample → record; у нас выходило
sample → **подмена корня** → record. Модель видит «я не повернулся» при команде
«повернись», каждый чанк пытается довернуть, поворот стирается, остаток копится в
локальных поворотах костей — и сбрасывается, когда команда уходит в idle.

Замер `tools/verify_pose_stability.py` (круг 12 × 0.5 s на 5 м/с, затем 1 s простоя;
метрика — угол локального поворота кости относительно bind, т.е. свойство позы, а не
пространства):

| Пик по кругу | было (root в историю) | стало (root модели в историю) |
|---|---:|---:|
| spine | 45.7° | 28.5° |
| chest | 78.4° | 30.8° |
| thigh.L | 134.3° | 94.6° |
| arm.R | 178.3° | 71.2° |
| восстановление на простое | нет (arm.R 115°) | да |

Колонка «стало» здесь снята при **старом** контракте ground (§4.7), который на тот момент
ещё не был исправлен. С полным исправлением (§4.6 + §4.7) те же пики: spine 14.5°,
chest 19.6°, thigh.L 63.9°, arm.R 80.8° — см. таблицу в §4.7.

Исправление: `_apply_external_root` вызывается **после** `record_pose` /
`seed_history_from_pose`, поэтому в историю модели идёт её собственный корень, а
выровненный корень получает только поза, которую мы отдаём в Unity. Контракт §4.5 не
нарушен: `verify_root_frame.py` по-прежнему `PASS`, `delta_root = 0.0°` на idle, 5 м/с и
после поворота на 90°.

**Честная оговорка про guard.** `--legacy-order` (контрфакт «root в историю», но с уже
исправленным ground из §4.7) даёт chest 23.8° против 19.6° у рабочего кода и **не**
превышает порог 40°, т.е. сам по себе порядок записи — улучшение примерно на 4°, а не
разница «FAIL/PASS». Разница 28.5° → 19.6° в таблице выше набрана двумя правками вместе
(порядок + владение ground/velocity), и разделяет их только `--legacy-ground`.

**Инвариант:** в `record_pose` уходит поза, которой владеет модель. Любая внешняя правка
корня (позиция, ориентация) применяется только к пакету, после записи истории.

### 4.7. Владение ground/velocity (fix 17.11, третий)

Симптом: «отпускаешь кнопки — его раскручивает», «нереальная физика», «как dummy на
нитке». Это остаток того же закручивания, но уже не из порядка записи.

Причина — sidecar **присваивал модели чужую землю**: перед сэмплом в
`character.character_ground_position` писался `app_ground` (позиция игрока из Unity), а
`actual_velocity` вычислялась из скорости игрока. Официальный `Character.step()`
(`app/runtime/common/character.py:196-206`) делает наоборот:

```
state_machine.update → previous_ground = character_ground_position.copy()
→ _sample_playback → _update_character_velocity(previous_ground, dt)
→ record_pose → _update_probe_box
```

а `_update_character_position()` (строка 404) сам пишет в `character_ground_position`
собственный корень модели. В нашей версии получалась внутренне противоречивая история:
собственный корень модели в позе едет вперёд на 5 м/с, а `actual_velocity`, которую читает
state machine, при отпущенных клавишах ровно 0. Модель честно отрабатывала «меня тянут,
но я стою», и разница уходила в локальные повороты корпуса — которые и раскручивались на
простое.

Исправление (`runtime_sidecar.py::step_character`):

- убраны обе строки `character.character_ground_position[:] = app_ground`;
- убран синтез `previous_ground = app_ground - app_velocity * dt`;
- `previous_ground = character.character_ground_position.copy()` снимается **до**
  `_sample_playback`, как в официальном коде — то есть скорость считается по движению
  собственного корня модели между кадрами.

Мир при этом по-прежнему принадлежит игроку: позицию и ориентацию в Unity задаёт только
`_apply_external_root`, уже после записи истории, и `CharacterController` остаётся
единственным источником движения.

Замер `tools/verify_pose_stability.py` (круг 12 × 0.5 s на 5 м/с, затем 1 s простоя;
`--legacy-ground` воспроизводит старый контракт на том же коде и том же вводе):

| Метрика | `--legacy-ground` (было) | рабочий код (стало) |
|---|---:|---:|
| spine, пик | 28.54° | **14.45°** |
| chest, пик | 30.84° | **19.63°** |
| thigh.L, пик | 94.63° | **63.86°** |
| thigh.R, пик | 106.52° | **84.21°** |
| arm.L, пик | 102.0° | **92.92°** |
| arm.R, пик | 71.18° | 80.83° |
| bodyLean, пик | 41.44° | **21.49°** |
| spine, простой | 14.4° | **4.65°** |
| chest, простой | 26.13° | **5.61°** |
| thigh.R, простой | 53.19° | **14.96°** |

Пики детерминированы (повторные прогоны дают те же 14.45 / 19.63 / 21.49); гуляет только
хвост простоя (chest 5.61° против 11.74° в другом прогоне). Картина по пикам смешанная:

**Инвариант:** `character_ground_position` и `actual_velocity` принадлежат модели — их
считает её собственный `_sample_playback`; позиция игрока в них не попадает никогда.

### 4.8. Направления конечностей и двойной поворот ключицы (fix 17.11, четвёртый)

Жалоба «руки напутаны, ноги ведут не туда» до сих пор не была ничем измерена: §4.6 меряет
только МАГНИТУДЫ локальных дельт, §4.5 — только корень. Добавлен харнесс
`tools/verify_pose_directions.py`: он считает FK из пакета в той же системе, в которой
строит C# (`ToUnityPos`/`ToUnityRot`; down = −Y, forward ≈ +Z), и меряет направления
сегментов на прямом ходе 5 м/с после разогрева (180 кадров).

Первое, что выяснилось: **поза от самой модели корректна**.

| Метрика (180 кадров прямого хода 5 м/с) | Значение | Смысл |
|---|---:|---|
| `arm_down_deg` | 35.2° (L 33.8 / R 36.7) | руки опущены (в bind они горизонтальны ±X) |
| `thigh_down_deg` | 27.7° (L 28.5 / R 27.0) | бёдра вниз |
| `thigh_scissor` | **−0.902** | ноги в противофазе |
| `arm_leg_same_L` / `_R` | −0.914 / −0.886 | контралатеральность рука↔одноимённая нога |
| `arm_pair` | −0.986 | руки качаются друг против друга |
| `upperArm_L_x` / `_R_x` | −0.362 / +0.387 | левая и правая по разные стороны |
| `toe_L_z` / `toe_R_z` | 0.689 / 0.687 | носки смотрят вперёд |
| `spine_up_deg` | 4.65° | корпус вертикален |

То есть «руки напутаны / ноги не туда» — **не** следствие выхода модели: из неё идёт
обычный контралатеральный ход в наших осях. Также `arm_extra`
(`upperArm_L_x = −0.362` против `upperArm_R_x = +0.387`) показывает, что лево/право не
перепутаны местами.

Второе — найден реальный дефект в ретаргете. `MotionBricksSomaRetarget.Apply` домножал
поворот ключицы НА дельту всей цепи руки:

```csharp
foreach (int chainPose in ClavicleChains[i])
    _deltaByPose[chainPose] = swing * delta;   // upperArm, forearm, hand
```

Но `delta = frameWorld · bindWorld⁻¹` — это уже ПОЛНЫЙ мировой поворот кости: он сам
приводит сегмент руки в направление источника (`delta · bindDir` = направление сегмента
в кадре). Второй поворот `swing` — лишний. Замер: `swing` 7.9°, лишний поворот плеча
**6.8°** (L 6.9 / R 6.7) на обычном ходу. При поднятой руке `chest→shoulder`
поворачивается сильно, `swing` упирается в `MaxClavicleDeg = 45°`, и рука уезжает на все
45° — это и есть «руки напутаны» на подъёме.

Исправление: ключица двигает только свою кость `B-shoulder`; домножение цепи удалено,
`ClavicleChains` больше не нужен. Компиляция — чистая (`No compile errors`).

**Оговорка:** снятие лишних 6.8° на ходу визуально может быть незаметно; главный эффект

### 4.10. Приёмка 18:49–18:5x: yaw эталона и «задом наперёд» (fix 17.12)

Жалоба: «после резких WDSAW… и серии прыжков персонажа всего перекоребило, стал задом
наперёд, руки шиворот навыворот». Плюс диагностика из игры:

```

serverStep=1,3 ms, fallbacks=0, hitches=0
sent=958 (15,5/s), received=867 (14,1/s), age=14,7 ms, RTT p50=2,5 p95=15,2 ms,
generations=156, inference last/p50/p95/max=8,2/9,0/46,3/97,5 ms, malformed=0
```

**(а) Корень зависел от yaw, зафиксированного при RESET.** `model_pose` снимает `inv(app_rotation)`,
а `_apply_external_root` клал в корень `app * inv(ref) * M * bind`, где `ref` — yaw игрока в момент
RESET. Сокращение даёт `M^-1 * inv(ref) * M * bind`, то есть постоянный поворот корня,
когда RESET случился не на yaw 0. А RESET делается ровно на airborne STOP/START:
в логе видно четыре пары `STOP: airborne` → `START` сразу после Attach. Отсюда:
развернулся → прыгнул → корпус завален навсегда, до следующего случайного RESET.

Измерено `verify_root_frame.py` (новая фаза `reset180`: RESET на yaw 180° посреди разворота):

| | delta_root |
|---|---:|
| после правки (`max_delta_root_deg_after_reset_yaw180`) | **0.0°** |
| старый контракт (`pre_fix_reset_yaw_counterfactual`) | **180.0°**, ось `(0,-1,0)` |

Ровно «задом наперёд». Правка: `_reference_app_rotation` удалён, `corrected_rotation =
app_rotation * M * bind` — корень в пакете тождественно равен `model_to_runtime * bind_root`
при любом yaw, и `delta_root = 0` всегда (все 270 кадров, включая RESET на 180°).

**(б) `contacts=0` в логе — не потеря контакта.** Замер всей стойки: `contacts_max` =
**0.0 в idle** (клип) и **1.0 в движении**. Канал живой; в лог попал кадр покоя
(`source=clip`). Контакты в C# сейчас вообще не используются для IK — скольжение от них не зависит.

**(в) `sent=15,5/s` — это 15 fps редактора.** Поза обновляется 15 раз в секунду, отсюда
ступеньки; модель тут не при чём (`serverStep=1,3 ms`, `inference p95=46,3 ms`).

**(г) Первые секунды после Attach — подъём sidecar, а не модель.** `START` → `ENGINE_READY
init_ms=3303` (это только ENGINE; до него ещё ~4 с на python + импорт Warp). Всё это время
пакетов нет, и игрок едет на authored Animator. Добавлена метка
`[MB-Runtime] LIVE: первый пакет через N мс` и поле `firstPose=` в диагностике — теперь окно
видно числом, а `START` сразу предупреждает, что надо ждать `LIVE`.

**Инвариант:** yaw игрока не входит ни в эталон, ни в корень пакета (`delta_root = 0` при любом
RESET); нули в `contacts` в покое — норма, а не потеря контакта; `LIVE` — момент, с которого
нейрослой реально рулит позой.

### 4.11. Задержка: что проверено и что оказалось причиной (fix 17.13)

Жалоба: «анимация будто в лаге, бег проигрывается как ходьба, всё идёт с латентностью 1+ с».
Диагностика:

```
active=True, source=clip_transition, sequence=256, contacts=0,51/0,66/0,59/0,96,
serverStep=2,3 ms, fallbacks=0, hitches=0, firstPose=7317 ms
sent=257 (14,6/s), received=143 (8,1/s), age=13,0 ms, RTT last/p50/p95=3,3/2,2/12,5 ms,
generations=14, inference last/p50/p95/max=29,9/6,7/29,9/94,7 ms
+ девять подряд START pid=14528 (один и тот же процесс)
```

**(а) Гипотеза «очередь теряет время» проверена и ОПРОВЕРГНУТА.** `serve()` до этого брал из
пачки только новейший запрос, остальные выбрасывал вместе с их `dt` — арифметика по логу
(`received` 8,1/s при `sent` 14,6/s) обещала потерю почти половины времени модели.
`verify_udp_pacing.py` поднимает настоящий `serve()` в потоке и гоняет клиента на 15 Hz:

| режим | обработано | sim/wall |
|---|---:|---:|
| legacy (latest-only) | 91 из 91 | **1.011** |
| in-order, каждый кадр со своим dt | 91 из 91 | **1.011** |

То есть очередь не накапливается и время не теряется. Разбор всё равно переведён на
in-order (`take_burst`, до `MAX_CATCH_UP_FRAMES = 8`): это не меняет поведение сейчас, но
не теряет время, если затор возникнет (генерация до 95 ms). Ловушка зафиксирована, чтобы
её больше не принимали за причину.

**(б) Причина видна двумя строками.** `age=13,0 ms` — поза на клиенте свежая, поток не опаздывает.
А `START pid=14528` повторяется **девять раз с ОДНИМ И ТЕМ ЖЕ pid**: процесс жив (правка
“не убивать на stale” работает), но каждый `START` ставил `_resetPending = true`, то есть
делал RESET: `_capture_reference`, пере-засев истории, рестарт state machine/клипа. Отсюда
`source=clip_transition` на 256-м кадре и `generations=14` за 17 с: модель почти всё время
заново входит в движение с нуля. Именно это читается как «задержка 1+ с» и «бег как ходьба».

Правка: `StartRuntime(bool hardReset = true)`; продолжение после приземления вызывает
`StartRuntime(hardReset: false)` — прыжок больше не сбрасывает модель, она продолжает свою
историю с того места, где была. Спавн/телепорт (>5 m) по-прежнему шлют RESET.

**(в) Контроль в следующем прогоне.** В диагностику добавлено `resets=`: число RESET за сессию.
Ожидание: несколько прыжков больше не увеличивают `resets` (только первый attach и реальные

**Инвариант:** RESET — только для нового заякоривания (старт, телепорт); возобновление после
airborne RESET’а не делает, иначе модель теряет фазу клипа и выглядит «запаздывающей».

### 4.12. RTT p50 = 1850 ms: очередь подъёма sidecar (fix 17.14)

Приёмка после §4.11: «задержка ровно та же». Лог:

```
active=True, source=clip, sequence=186, contacts=0,00/0,00/0,00/0,00, serverStep=1,2 ms
fallbacks=0, hitches=0, resets=1, firstPose=7261 ms
sent=187 (13,5/s), received=185 (13,4/s), age=14,3 ms,
RTT last/p50/p95=3,4/1850,5/6314,1 ms, generations=0, inference 0,0 ms
```

Что подтвердилось: `resets=1` — правка (б) из §4.11 работает, прыжки больше не сбрасывают модель;
`received 185` при `sent 187` — поток 1:1, ничего не выбрасывается.

Что вскрылось: **`RTT p50 = 1850 ms` при `age = 14,3 ms`**. `age` — это возраст *последнего
пришедшего пакета*, он ничего не говорит о возрасте его *содержимого*: пакеты идут непрерывно, но
приходят за старые запросы. RTT считается по `sequence` (`_pending[sequence]` на отправке,
`now - sent` при разборе), то есть это честное «отправил → разобрал».

Арифметика сходится с `firstPose`: подъём sidecar занимает 7,26 с, клиент в это время шлёт с частотой
кадра — 7,26 × 13,5 ≈ **98 запросов**. Sidecar в этот момент внутри `ExternalSOMACharacter(...)` и
сокет не читает; запросы ждут в буфере. После `ENGINE_READY` in-order разбор (§4.11) обрабатывает их
все — с их собственными (уже прошлыми) `dt`. Отсюда два следствия:

1. каждый ответ несёт старый `sequence` → RTT равен возрасту очереди (p95 6314 ms ≈ глубина очереди);
2. модель получает ~7 с уже прошедших команд одним залпом и только потом догоняет настоящее.

Правка: пока не пришёл **ни один** пакет, клиент шлёт пробу 2 раза в секунду
(`_warmupSendInterval = 0.5f`) — первый пакет по-прежнему запускает ENGINE, но очередь не растёт.
Throttle стоит **до** разбора `_resetPending`, иначе пропущенный кадр съедает стартовый RESET.
Дополнительно `MotionBricksRuntimeClient.ResetSamples()` очищает кольца RTT/инференса на каждом
`StartRuntime`, чтобы p50 не тащил в себя очередь подъёма.

**(в) Новая метрика `onset=`.** RTT меряет только транспорт; жалоба «нажал W — анимация пошла
позже» меряется от команды до первого кадра, где стопа реально в контакте (`max(contacts) > 0.5`;
в idle модель отдаёт `0,00` ×4, в движении доходит до `1,00`). В лог пишется
`[MB-Runtime] ONSET: команда движения → первый контакт стопы N мс (RTT p50=…, source=…)`.

**Контроль в следующем прогоне** (нужен прогон с движением — лог этой сессии снят в idle:
`source=clip`, `generations=0`, контакты нули):

| поле | ожидание | если не так |
|---|---|---|
| `RTT p50` | 10–20 ms | очередь осталась — смотреть `firstPose` и буфер сокета |
| `resets` | 1 на сессию | RESET идёт не только от attach/телепорта |
| `onset` | единицы–сотни мс | транспорт чист, латентность в отклике модели (state machine/бленд чанка) |

**Инвариант:** период пробы на подъёме не связан с частотой кадра; очередь запросов во время
`ENGINE` — это не «модель тормозит», а буферизация, которую нельзя отдавать модели целиком.

### 4.13. Остаток задержки — длина чанка, а не транспорт (fix 17.15)

Приёмка после §4.12:

```
LIVE: первый пакет через 3 мс после Start
ONSET: команда движения → первый контакт стопы 77 / 97 / 57 мс (RTT p50=2,3 ms, source=0)
```

Транспорт чистый и доказанно: RTT p50 2,3 мс, поза реагирует за один кадр (57–97 мс при 13 fps =
~74 мс на кадр), `source=0` — это `generated`, т.е. модель уже генерирует, а не крутит клип.
Сглаживания в C# нет (`LateUpdate` → `_retarget.Apply` пишет позу напрямую), `contacts` в пакете
берутся из того же `runtime.step`, что и поза, — метрика `onset` честная.

Остаток — конструкция самой MotionBricks: она работает **чанками** и генерирует вперёд.

| константа | значение |
|---|---|
| `MODEL_SAMPLE_RATE` | 30 Гц |
| `MODEL_POSES_PER_TOKEN` | 4 (0,133 с) |
| `MODEL_MIN/MAX_TOKEN_COUNT` | 6 … 16 |
| чанк в валидных кадрах | `tokens*4 − 6` → **0,6 … 1,9 с** |

Проигрывается уже сгенерированный чанк, поэтому команда, пришедшая в середине чанка, будет
отработана только к точке перехода (`time_to_transition`). Замер по логу: `generations=14` за 17 с
≈ 1,2 с на чанк — это и есть наблюдаемая «1+ с», и она же объясняет «бег проигрывается как ходьба»
сразу после Shift: играется чанк, сгенерированный ещё по команде шага.

**Инструментовка.** В зарезервированном `uint32` заголовка (поле было в структуре, клиент его
пропускал) теперь едут две величины: младшие 16 бит — `playback_duration` в мс, старшие 16 —
`time_to_transition` в мс. Размер пакета не изменился (48 + 2156 + 16 = **2220 Б**). В диагностике
появилось `chunk=<длина>/<остаток> ms`, а в авто-логе — `gen/s`.

**Авто-лог.** Диагностику в движении хоткеем не снять (руки на WASD), поэтому `Diagnostics()` +
`gen/s` пишутся сами каждые `_autoLogIntervalSeconds` (5 с, 0 — выключить).

**Что решают следующие цифры:** если `chunk` ≈ 1200 мс и `gen/s` ≈ 0,8 — потолок задаёт чанк, и
рычаг один: сокращать горизонт генерации (меньше токенов / реже целевая поза), а не сокет.

### 4.14. Задержка в отклике модели: halflife 0.6 с и пороги регенерации (fix 17.16)

- чтение настроек обратно — `0.1 0.1 0.06 0.06 0.05 0.02 0.995`; с `--engine-defaults` — `0.6 0.92`;

### 4.15. Замер шага скорости: виноват не тот объект LocomotionSettings (fix 17.17)

`verify_step_response.py` меряет **путь, который модель проходит за кадр** (то, что видно
глазом), на сценарии `idle 1.5 с → walk 5 м/с 3 с → run 10 м/с 3 с`:

| пресет | t50 idle→walk | t90 | t50 walk→run | t90 run | уст. walk | уст. run | gen/s |
|---|---:|---:|---:|---:|---:|---:|---:|
| engine-defaults | 1917 мс | 2967 мс | 2017 мс | не достигнут | 4,05 м/с | 8,79 м/с | 1,60 |
| **movement-only (новый дефолт)** | **1067 мс** | **2250 мс** | **850 мс** | **1900 мс** | **4,43 м/с** | **9,80 м/с** | 1,47 |
| responsive-full (§4.14) | 1050 мс | 1733 мс | 867 мс | 1917 мс | 4,41 м/с | 9,78 м/с | 4,68 |
| short-chunk (6 токенов) | 550 мс | 850 мс | 217 мс | 250 мс | **9,49 м/с** | **18,48 м/с** | 3,88 |

Разброс между прогонами ±100–150 мс, поэтому сравнивать можно только строки одного прогона.

**Главная находка: §4.14 правил не тот объект.** Полураспады читает `Movements._smooth`
из **`character.movement.settings`** — это отдельный экземпляр `LocomotionSettings`, а
`state.settings` держит только пороги регенерации. `apply_response_settings` патчил только
состояния, поэтому в первом замере полураспады «не влияли» — оверрайд до них не доходил.

Трассировка по кадрам это подтверждает: `desired_speed` при команде 5 м/с доходил до 4,96
за **1,35 с** с движковым halflife 0,6 с и за **0,5 с** с 0,10 с.

Итог правки (дефолт `MOVEMENT_SETTINGS`, только полураспады):

1. **Включение бега: t50 2017 → 850 мс, t90 с «не достиг» → 1900 мс.** Это и есть «бег
   проигрывается как ходьба 2–3 секунды».
2. **Скорость установившегося шага 4,05 → 4,43 м/с** при команде 5 — слайд 19% → 11%.
3. **Цена нулевая:** `gen/s` 1,60 → 1,47, `step_wall_ms p95` 1,97 → 2,36 мс.

Пороги регенерации из §4.14 **откачены на движковые**: над `movement-only` они дают в пределах
разброса (t90 walk 2250 → 1733 мс — единственное возможное преимущество), но стоят ×3
генераций и поднимают `step_wall_ms p95` до 6,5 мс. Включаются только флагом `--responsive`.

**Что осталось.** `allowed_token_counts=(6,)` — не горизонт, а селектор динамики: `chunk 233 мс`
и разгон 0,2–0,5 с, но модель проезжает 9,49 м/с вместо 4,43 (×2,1) — так выпускать нельзя.
Поэтому `chunk` намеренно остаётся движковым (0,77–1,3 с). **→ Решено в §4.16:** сокращать
токены нужно **вместе** с `position_scale`.

**Вторая, ещё не объяснённая аномалия** — из той же трассы: при `chunk=1300 мс` и всего 11–12
генерациях за 7,5 с `rem` (`time_to_transition`) дёргается 1283↔1267 каждые 2 кадра, то есть
сбрасывается чаще, чем допускает счётчик генераций (`generate()` ставит `playback_time = 0`).
Пока не выяснено, откуда берётся этот сброс, — следующий шаг, и именно он отвечает за остаточные
2–3 с до полной скорости.

**Что это значит.** `CharacterController` выходит на 5–10 м/с за один кадр, а анимация догоняет
1–2 с. В официальном приложении персонаж едет со скоростью анимации — там рассогласования нет.
Отсюда и «слайдит», и «бег играет как ходьба»: это не транспорт и не сокет
(`RTT p50 2,1–2,4 ms`, `onset 110–232 ms`), а разница скоростей тела и анимации.

### 4.16. Отклик в рантайме: горизонт генерации, а не транспорт (fix 17.18)

Симптом приёмки 17.11: «нажимаю W — персонаж слайдит без анимации, через секунду начинается
проигрывание; и так во все переходные стадии, явная латентность и резиновость». Лог того же
прогона транспорт и инференс исключает: `RTT p50 2,0–2,4 ms`, `serverStep 1,3–2,2 ms`,
`inference p50 8,0–8,3 ms`, `resets=1`, `age 16–63 ms`. Остаток — в том, **что** модель получает на
вход и **на какой горизонт** её просят сгенерировать.

Пять механизмов, каждый проверен трассировкой 60 Гц:

| # | Механизм | Следствие |
|---|---|---|
| а | `LocomotionState.enter()` делает `realign(character.actual_velocity)`, а в `IdleState` `actual_velocity == 0`, и обнуляет `desired_speed` | первый кадр нажатия W сбрасывает скорость в 0 и генерирует холостой чанк в 100% `Idle` |
| б | вторая генерация на микроскорости; порог `max(Δдиапазона × 0,3, max_speed × 0,1)` не пропускает остаток до `walk_speed` | тело уже 5 м/с, модель держится на 0,01 м/с |
| в | `position_scale = 1,0` ставит конец чанка на **секунду** хода вперёд, `endpoint correction` пришивает начало чанка к статичному контексту | первый метр модель почти стоит — это и есть слайд |
| г | `playback_time = 0` на каждой регенерации при `gen/s 3–4` | фаза клипа перезапускается 3–4 раза в секунду |
| д | `generate_clip_transition()` ставит вход в idle-клип на `character_ground_position + actual_velocity` (на секунду вперёд) при `chunk 1633 мс` | после отпускания клавиш анимация ещё полторы секунды едет вперёд |

**Правка** — пять согласованных изменений в `runtime_sidecar.py`:

```python
RESPONSIVE_TOKEN_COUNTS = (6, 7)          # горизонт 0,8–0,93 с вместо 1,07–2,13 с
RESPONSIVE_POSITION_SCALE = 0.58          # путь чанка × 0,58 — во столько же короче горизонт
RESPONSIVE_TRANSITION_EARLY_FRAMES = 4    # вход в клип на 4 кадра раньше
CLIP_TRANSITION_HORIZON_SECONDS = 0.25    # вход в idle-клип на 0,25 с вперёд, а не на 1,0 с
MAX_INTERNAL_STEP_DT = 1.0 / 60.0         # субшаги: 15 FPS редактора = 4 внутренних шага
```

1. `apply_token_horizon(character, token_counts, position_scale=None, transition_early_by_frames=None)`
   правит `allowed_token_counts`, `position_scale` и `transition_early_by_frames` **одновременно**
   (см. ловушку ниже). Возвращает число пропатченных режимов → в отчёте стенда это `token_patches`.
2. `install_immediate_locomotion_enter(character)` подменяет `enter` у `standing_locomotion_state` и
   `crouching_locomotion_state`: при `input_speed > 0` выравнивание по `movement.input_velocity`, иначе
   по `actual_velocity`. Снимает (а).
3. `MOVEMENT_SETTINGS`: `facing_halflife 0.02`, `velocity_direction_halflife 0.015`,
   `speed_acceleration_halflife 0.015`, `speed_deceleration_halflife 0.02`,
   `speed_regeneration_fraction 0.15`, `minimum_speed_regeneration_fraction 0.05`,
   `direction_regeneration_dot 0.92`, `maximum_direction_change_speed_reduction 0.0`. Снимает (б).
4. `generate_clip_transition()` в нашем подклассе ставит вход в клип на
   `actual_velocity * CLIP_TRANSITION_HORIZON_SECONDS` и генерирует с
   `_fast_clip_transition_params`; `LINEAR_LOCOMOTION.minimum_speed = 0,8 × walk_speed`. Снимает (д).
5. `step_character()` делит кадр на субшаги `ceil(dt / 16,7 ms)`: в каждом — `state_machine.update`,
   `_sample_playback`, `_update_character_velocity`, `record_pose`; `_apply_external_root` и
   `_update_probe_box` — один раз после цикла. При 15 FPS Unity модель ведётся как при 60 FPS, а не
   прыгает шагами по 67 мс.

**Замер** `verify_step_response.py --preset movement-only` (сценарий `idle 1,5 с → walk 5 м/с 3 с →
run 10 м/с 3 с`):

| метрика | до (§4.15) | после | |

| t50 idle→walk | 1066,7 мс | **150,0 мс** | ×7,1 |

| t50 walk→run | 850 мс | **350,0 мс** | ×2,4 |

| уст. run | 9,797 м/с | **10,004 м/с** | |

`verify_motion_contract.py` (тот же режим, `engine_defaults=False`): `onset_frames 13` = **220 мс**
от команды до начала маха при пороге `idle_swing_baseline 0,0948 + 0,12`, `model_speed_mps 4,969`
при команде 5,0 (`slide_ratio 0,994`), `model_root_displacement_m 12,34` за 300 кадров,

`(6,7) / 0,58 / 4` выбран как компромисс: самый короткий горизонт без перелома шага (`thR` 86,2° —
в пределах §4.6) и установившаяся скорость совпадает с командой. Выбранная точка перепроверена
сегодня финальной сборкой стенда: `t50 150,0 мс`, `steady_walk 4,981 м/с`.

**Ловушка (главная).** `allowed_token_counts` нельзя сокращать без `position_scale`: `endpoint
correction` ставит конец чанка на `target[0]`, то есть на `desired_velocity × velocity_scale ×
position_scale`. С `(6,)` и `position_scale 1,0` модель проезжает **9,49 м/с** вместо 4,43 — та
самая «резиновость», которую потом ищут в ретаргете. Отсюда три аргумента в `apply_token_horizon`
одновременно и `token_patches 3` в отчёте.

**Приёмка 17.11 (fix 17.18): основной задержки больше нет.** Лог живого Play Mode:

```
firstPose = 264 мс     (ENGINE уже был поднят; 7558 мс в §4.12 — это подъём, а не модель)
ONSET     = 45 и 105 мс, source=0 (generated)   — раньше было 117…205 мс и ложные 0 мс
chunk     = 433…567 мс (было 500…1633), gen/s 3,2…5,2
RTT p50   = 4,7…4,9 мс, inference p50 9,4…10,8 мс, fallbacks 0, hitches 0
```

Вердикт пользователя: «пропала основная задержка». Остаток — качество самой позы:
«бегает как будто не суставы, а пружины» — это следующий этап (упругость, пере-/недобор
амплитуды в суставах), к отклику он не относится.

**Что осталось.**

- `ONSET` в `MotionBricksRuntimePlayback.cs` по-прежнему означает «первый кадр, где стопа в контакте»,
  а не «мах начался». Ложные `0 мс (source=1)` убраны: кадр, лежавший в буфере до нажатия (в
  `clip_transition`/клипе стопа уже стоит), больше не засчитывается — сверяется
  `_lastAppliedSequence > _onsetSequenceAtCommand`. Смысл метрики при этом прежний.
- Визуальная приёмка на живом персонаже не проводилась. В C# изменён только счётчик `ONSET`
  (компиляция чистая); ретаргет, протокол и проигрывание не трогались.
- Аномалия §4.15 с `rem` 1283↔1267 каждые 2 кадра не объяснена до конца; правка снизила частоту
  (`gen/s` 3–4 → 2,14), но сам сброс — тот же `playback_time = 0` в `generate()`.

## 5. Ручная приёмка

1. Войти в Play Mode → Host/Client, дождаться появления персонажа.
2. `ProjectC/MotionBricks/Runtime/Attach + start on my player`.
3. Проверить WASD, Shift, резкие повороты, stop, прыжок/падение и движение по неровной поверхности.
4. `Ctrl+F10` — сравнить neural preview с обычным Animator; повторить несколько раз.
5. `ProjectC/MotionBricks/Runtime/Log diagnostics` — сохранить строки `[MB-Runtime]`
   и `[MB-Sidecar]`, включая p95, generations, source, fallbacks и RAM.
6. Отдельно проверить стопы/контакты, equipment, body swap, каст, F8/F9 и выход из Play Mode.
7. После body swap повторить Attach вручную. Для завершения — `Detach`.

Для оценки нагрузки дополнительно нужны Unity CPU/GPU frame time, FPS, VRAM и длительный
прогон; затем host-client 1/2/4 игрока. Сейчас эти данные не собраны.

## 6. Что ещё не доказано

- **Play Mode и визуальный retarget на живом персонаже не запускались агентом.**
- Нет оснований заранее заявлять отсутствие T-pose, skating, penetration, pop или проблем
  с пропорциями/ключицами.
- Runtime IK ног в Unity не добавлен; модель выдаёт contacts, но это не гарантирует контакт
  после ретаргета.
- Equipment, body swap, combat fallback, Floating Origin, выгрузка и выход из Play Mode
  требуют ручной проверки.
- GPU/VRAM/FPS в Unity, host-client 1/2/4 и длительная стабильность не измерены.
- Это evaluation sidecar с абсолютными dev-путями, а не нативный shipping backend.

Следующее решение принимается по визуальной приёмке и полным игровым замерам, а не по
standalone inference latency.
