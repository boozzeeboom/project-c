# T-PAROM-20 — персистенция парома между сессиями (дизайн)

> Статус: дизайн (T-PAROM-20). Реализация — следом, только этот тикет
> (T-PAROM-21 игрок-на-тележку и T-PAROM-22 защита от падений — отдельно).
> База: `ShipPositionServer` (тик 5 с, restore 3.5 с), `ShipPositions.json`
> (`ships[] + players[]`), `ParomRoute` (симуляция `s/dir/station/dwelling`).

## 1. Цель

После рестарта сервера кабинка продолжает с сохранённой точки маршрута
(`s`, направление, станция, стоянка), а не с начальной (`s=0` в
`OnNetworkSpawn`). Без пассажиров в момент рестарта никого не телепортируем —
только состояние ветки. Игроков касается лишь порядком (ресторр парома раньше
ресторра игроков, см. §4).

## 2. Что сохраняем (4 числа + identity)

Состояние ветки — скаляры симуляции сервера:

- `s` — метры от старта; `dir` (+1/−1); `station` — индекс текущей станции;
- `dwelling` + `dwellRemaining` — стоит ли и сколько осталось стоять.

Идентификатор ветки `routeId`: новое поле на `ParomRoute`, авто-фолбэк
`Scene.name + "/" + gameObject.name` (стабильно без работы в инспекторе;
несколько веток различаются; переименование ломает матчинг — задокументировано,
валидация по `sceneName` как у кораблей).

## 3. Куда и когда (переиспользуем, не плодим)

- DTO `ParomRouteSaveData` рядом с `ShipPositionSaveData`
  (`routeId, sceneName, s, dir, station, dwelling, dwellRemaining, savedAtUnix`);
  список `paroms` в `ShipPositionListWrapper` — JsonUtility подхватит сам,
  старые файлы без `paroms` читаются (null → пропуск).
- Save: тот же 5-с тик `ShipPositionServer.SaveCurrentState`
  (`FindObjectsByType<ParomRoute>`, только `IsSpawned`; несколько веток —
  несколько записей, копейки).
- Restore: в `RestoreCoroutine` рядом с кораблями (до 3.5-с барьера игроков):
  матчинг `routeId` (+ `sceneName`), применение через публичный
  `ParomRoute.ApplyRestoredState(...)`. Нет записи — сцена как есть.
  Только сервер (`IsServerSafe`); клиенты следуют через `_netS`.

## 4. Порядок и зависимости

Спавн сценовых объектов (есть) → restore паромов + кораблей (~3.5 с) →
restore игроков (спавн + 5 с, читают кабинку живьём). Строгой зависимости
нет (игрок читает живую позицию), но паром раньше игроков — инвариант.

## 5. Floating Origin

`s` — скаляр вдоль пути, якоря живые: кумулятив сдвига НЕ нужен
(в `ShiftWrapperByOffset` список `paroms` намеренно не трогаем —
комментарий в коде). Позиция кабинки после рестарта вычисляется из живых
якорей + `s`, как всегда.

## 6. Не входит (следующие тикеты)

- T-PAROM-21: телепорт игрока на живую кабинку (сохранённый `platformRouteId`,
  переинициализация кэша carry).
- T-PAROM-22: защита от падений (platform-rescue по образцу ship-rescue).
- NPC на пароме: тот же путь позже.
- Разгон/торможение, несколько кабинок: не трогаем.

## 7. Проверка (пользователь)

1. Console → 0 errors.
2. Запустить хост, дождаться отъезда кабинки от A (s > 50), остановить сервер,
   запустить снова → кабинка продолжается с ~того же `s`/`dir` (лог restore),
   а не с A.
3. Удалить/повредить запись `paroms` в `ShipPositions.json` → старт как обычно,
   ветка с начальной (graceful, без ошибок).
