## 2. Где это в сцене

```
WorldRoot_0_0
├── PRIMUM/                                  ← инстанс PRIMUM_CITY.prefab (НЕ ТРОГАЕМ)
│   └── <чанк>/DOORS/<имя>                   ← 3 038 исходных групп, ВЫКЛЮЧЕНЫ
└── PRIMUM_DOORS/                            ← ✅ новая расстановка, 21 узел-чанк
    └── PRIMUM_HOUSES_S7_SE_P1_46H/
        └── RES_SE_12_DOOR_LEAF_1.02x2.25_X  ← префаб-инстанс, пивот = низ по центру
```

**Почему отдельный корень, а не внутрь чанка города:**

1. `PRIMUM` — инстанс префаба; добавление детей создаёт **префаб-оверрайды** (в тестовом пилоте их было 10,
   при 2 148 сцена распухла бы и правки города стали бы хрупкими).
2. Отдельный корень легко выделить, посчитать, скрыть и **снести целиком** (`Очистить расстановку`).
3. `PRIMUM_DOORS` лежит под `WorldRoot_0_0` → **едет при ребейзе мира** вместе с городом бесплатно
   (см. `docs/world/floatingorigin/09S_NEW_CONTENT_PIPELINE.md`).
4. Внутри — по узлу на чанк: удобно включать/выключать/чинить город частями.

## 3. Ground truth — геометрия сцены, а не реестр

Расстановка читает **не** CSV-реестр, а сами выключенные группы `DOORS/<имя>` в сцене. Причины:

* реестр — снимок из Blender; в сцене объекты уже с масштабом **k = 1.07** и мировыми координатами;
* **`rot_y` в реестре НЕ годится для ориентации префаба**: у 2 648 из 3 038 дверей там `180°` — это
  унаследованный поворот корня города, а не направление стены. Реальное направление стены определяется
  по мировому AABB двери (см. §4). Реестры остались документацией/провенансом.

Реестр `registries/doors_registry_*.csv` — по-прежнему полезен: имена, позиции, w/h, verts — совпадают
со сценой, по нему удобно сверять и искать дверь глазами.

## 4. Алгоритм (что делает инструмент)

Для каждой выключенной группы `DOORS/<имя>`:

1. **Мировой AABB** (`Renderer.bounds`): `size = (dx, dy, dz)`; повороты у дверей кратны 90°, поэтому AABB
   осевой и точный.
   * `H = dy` — высота;
   * `W = max(dx, dz)` — ширина проёма;
   * `T = min(dx, dz)` — толщина;
   * **ось толщины:** если `dx ≤ dz` → толщина по X, иначе по Z.
2. **Ориентация:** префаб «смотрит» локальной **+Z**. Если толщина по X — дверь стоит в стене,
   идущей вдоль Z, → `rotY = 90°`; если толщина по Z → `rotY = 0°`.
   (Проверено косвенно: расхождение ширины после посадки ≤ 1.41 % — при ошибке оси оно было бы в разы.)
3. **Створки по островам меша.** Меш двери = склейка (полотно + рама + фурнитура), острова не сварены,
   поэтому связные компоненты = детали. Остров считается **полотном**, если:
   `высота ≥ 0.80 · H`, `ширина ≥ 0.30 · W` (отсекает косяки и ручки), `толщина ≤ 0.30 · W`.
   Дверь **одностворчатая**, если полотно ровно одно и его ширина `≥ 0.55 · W`.
   (Проверено на выборке: 1.05×2.19 / 0.86×2.19 → одно полотно на всю ширину; 1.50×2.31 / 1.80×2.56 →
   два острова по ~0.5 W = двустворчатая.)
4. **Фильтры** (все пороги — константы в начале класса):
   `0.60 ≤ W ≤ 1.38`, `1.80 ≤ H ≤ 2.90`, `T / W ≤ 0.45`, одностворчатость, и не мебель/наличник
   по имени (`FURN`, `DOORCASE`, `SCHRANK`, `WARDROBE`, `VITRINE`), не `GATE`.
5. **Выбор варианта** — минимум искажений: `score = |W / W_префаба − 1| + |H / H_префаба − 1|`,
   берётся лучший из трёх. На практике это даёт «по ширине»: ≤ ~1.00 → PLANK_A, ~1.00–1.10 → PANEL_B,
   > ~1.10 → ARCH_C.
6. **Масштаб:** `scale = (W / W_префаба, H / H_префаба, clamp(T / D_префаба, 0.6, 1.6))`.
   По X/Y — подгонка под проём от **общего** габарита префаба (значит префаб не вылезет за исходную
   дверь), по Z — под фактическую толщину, чтобы рама села в откос.
7. **Позиция:** `(center.x, min.y, center.z)` — низ по центру, как у префаба.
8. **static = false** на инстансе и всех детях (`StaticEditorFlags = 0`) — жёстко, иначе при F8
   объекты «отрываются» от города (это и был баг, который заказчик нашёл на пилоте).

## 7. Ограничения / что учесть при визуальной приёмке

1. **Знак ориентации** (+Z или −Z, +X или −X) выбран соглашением, а не измерением: определить
   «улица/интерьер» по данным нельзя (у города нет коллайдеров стен после чистки физики).
   Поэтому створка может распахиваться **не в ту сторону** и петли могут оказаться не с той стороны.
   Лечится массово: добавить в инструмент таблицу разворотов по имени/чанку (или флаг «mirror»
   на конкретных дверях) — точечно правится `DoorController` (`hingeSide`, знак `openAngle`).
2. **`ADMIN` пуст** — там нет ни одной одностворчатой двери ≤ 1.38 м (1.80 двустворчатые, 1.41 `ADM_CONN`,
   1.60 будка, 12.63×4.17 парадный проём). Нужен отдельный набор «администрация».
3. **413 широких + 45 двустворчатых + 40 ворот** — следующие типы префабов: 1 двустворчатая,
   1 ангарная/ворота, набор «дворцы» (GLD/парадные).
4. **63 узких (0.56 м)** — узкий тип либо оставить как есть (проём пустой, исходная группа выключена).
5. **Все 2 148 инстансов — `Connected` префаб-инстансы**: правка префаба меняет все двери сразу.
   Материалы/меши префабов в git не лежат (`*.prefab`, `*.fbx` в `.gitignore`, живут в Lore VCS) —
   поэтому спецификация и этот инструмент и есть способ пересоздать всё 1:1.

## 11. Ревизия после визуальной приёмки (та же дата)

Заказчик посмотрел город и нашёл три класса дефектов. Все исправлены прогоном ред. 2.

### 11.1 «Двери в половину ширины проёма» — `TRD_S_48_DOOR_LEAF_0.77x2.46_X`

**Причина:** конвейер v13 разложил одну двустворчатую дверь торговой аллеи на **две группы-створки**
(`<дом>_DOOR_LEAF` и `<дом>_DOOR_LEAF_L`: 0.77 + 0.56 м). Расстановщик ставил префаб в каждую группу
отдельно, а вторая створка (0.56 м) вообще отбраковывалась как «узкая» → в проёме 1.24 м стояла
дверь 0.77 м, остальное — дыра.

**Исправлено:** сопряжение пар (`MergeLeafPairs`) — две соседние копланарные группы с общим низом,
зазором ≤ 0.12 м и общей шириной 1.15–1.75 м превращаются в **один проём**, куда ставится
двустворчатый префаб (`04_DOUBLE_DOOR_PREFAB.md`). Сопряжено **80** пар: TRD_P1 28, TRD_P2 26,
TRD_P3 26.

### 11.2 «Подряд 2 одностворчатых узких» — `TRD_S_20_DOOR_LEAF_0.80x2.70_X`

Тот же корень, обратный симптом: обе створки проходили фильтр (0.80 и 0.68) и в проём 1.50 м
вставали две узкие двери с двумя рамами. Исправление то же — одна двустворчатая на проём.

### 11.3 «Часть зданий просто пропустил» — витрины/лавки в `…_M_M_LIME_WASH`

**Причина:** в торговых и жилых чанках есть группы-«витрины» шириной 3.5–6.7 м
(`RES_TN_02_DOOR_LEAF_6.67x2.51`, `RES_S2_02_TQ_DOOR_isl003_4.15x2.29`, `RES_N_01_INT_DOOR_2_1.87x2.32` …).
Это **не двери**, а фасадная сборка лавки (полотно + неподвижные панели/прилавок). Конвейер выключил
их как «двери», а префаб туда не встал → в фасадах остались сквозные дыры (то, что видно как
«целые куски зданий пропущены»).

**Исправлено — два разных решения по ширине:**

| Случай | Решение | Кол-во |
|---|---|---|
| Широкая группа **≤ 1.78 м** с одной створкой (дверь + неподвижная панель) | двустворчатый префаб на весь проём | 30 |
| Широкая группа **> 1.78 м** (витрина/лавка) | **исходная группа включена обратно** (`action=keep_original`), префаб не ставится | 73 |

`keep_original` по чанкам: TRD-S2 37, NQ 18, TRD-N 10, NE_P1 8.

> Это единственное отступление от правила «все исходные группы выключены»: для витрин выключение =
> дыра в фасаде. Позже, когда появится префаб «витрина/лавка», их можно будет заменить так же, как двери.
